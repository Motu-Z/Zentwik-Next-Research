# 安装、部署与维护系统需求

- 状态：Proposed（产品方向草案，待结合现有实现评估）
- 日期：2026-11-26
- 涉及产品：Zentwik Next
- 文档类型：产品需求 / 架构预研

## 1. 目标

建立统一的 Windows 安装与维护体系，覆盖首次安装、升级、修复、组件变更、卸载和部署模式转换。

用户可选择标准安装或便携部署。两种模式共享产品功能、配置格式和核心实现，不维护两套产品。安装体系应适配 Zentwik 现有运行架构，并保持进程结构简洁、资源占用可控。

## 2. 部署模式

### 2.1 标准安装（Registered）

- 支持当前用户（Per-user）和所有用户（Per-machine）安装。
- 支持自定义程序安装目录。
- 程序文件与用户配置、日志、缓存、历史数据分开存放。
- 可选创建开始菜单和桌面快捷方式。
- 可选开机启动、文件关联及协议关联。
- 注册 Windows 卸载信息，并支持独立维护程序。
- 升级时保留用户配置和数据。

### 2.2 便携部署（Portable）

- 不进行常规 Windows 安装注册，不要求注册卸载信息。
- 用户选择解压或部署目录。
- 默认将配置、日志及必要数据存放在便携数据目录。
- 支持复制、移动和多个独立实例。
- 不强制创建快捷方式、开机启动或文件关联。
- 仍可使用需要系统权限的功能；涉及 Worker 提权、计划任务或驱动时按 Windows 权限规则处理。

便携版不应是功能阉割版。两种模式的功能差异只来自部署方式、数据位置和系统集成条件。

便携模式应通过明确的部署标识识别，不以目录名称推断。

## 3. 安装与维护入口

采用两个独立程序入口，共享安装状态、组件清单和维护基础设施。

### 3.1 Zentwik Setup

负责首次安装与升级：

- 检测已有安装及版本。
- 检查 Windows 版本、系统架构、权限和磁盘空间。
- 选择标准安装或便携部署。
- 选择安装范围和程序目录。
- 选择可选组件。
- 检测并处理运行库及外部依赖。
- 下载、安装并验证所需文件。
- 执行安装或升级并显示进度与结果。

检测到已有版本时，应识别安装位置、部署模式和组件状态，进入适当的升级或维护流程，避免盲目覆盖。

### 3.2 Zentwik Maintenance

负责已有安装的维护，且必须能够独立于主程序运行：

- 修复程序文件及安装状态。
- 添加、移除和更新可选组件。
- 修改允许变更的安装选项。
- 卸载程序及其系统集成。
- 管理 Zentwik 自身的开机启动注册项和计划任务。
- 迁移或恢复用户数据。
- 输出维护日志和诊断信息。

即使主程序、UI 或 Worker 无法启动，用户仍应能够运行 Maintenance。

### 3.3 共享基础设施

Setup 与 Maintenance 共用：

- 安装实例与版本识别。
- 组件清单及依赖解析。
- 文件完整性检查。
- 下载与校验。
- 安装状态管理。
- 操作日志。
- 数据保护、迁移与回滚机制。

两个入口可以独立分发，但不维护两套互不兼容的安装状态。

## 4. 安装位置与用户范围

### 4.1 程序与数据目录

分别管理：

- 程序文件目录。
- 用户配置目录。
- 日志目录。
- 缓存目录。
- 历史数据目录。

程序安装位置变化不应导致用户配置和历史数据丢失。数据目录是否允许自定义，作为后续设计项确认。

### 4.2 安装范围

**Per-user：** 仅为当前 Windows 用户安装，优先使用用户级目录，尽量避免不必要的管理员权限。

**Per-machine：** 为整台计算机安装，使用适当的系统级目录；需要管理员权限时明确请求。不同 Windows 用户的数据应保持隔离。

## 5. 依赖与运行环境

安装前检查实际发布所需的环境，包括：

- Windows 版本与系统架构。
- .NET Runtime（若发布方式需要）。
- Visual C++ Redistributable（若组件需要）。
- WebView2 Runtime（若 UI 技术栈需要）。
- 必要驱动、硬件接口及系统权限。
- 目标目录权限和磁盘空间。

依赖检测结果区分：已满足、缺失、版本不兼容、架构不匹配、状态无法确认、需要提权或重启。

缺少依赖时，向用户说明用途和处理方式，并提供下载与安装。优先使用依赖维护方的官方分发渠道；显示依赖名称、版本、来源和进度。已满足要求的依赖不重复安装。

支持离线安装包。离线环境缺少依赖时，明确列出所需文件及获取方式。

## 6. 组件管理

组件清单应声明：

- 唯一 ID、名称、版本和说明。
- 适用平台与安装条件。
- 依赖及冲突关系。
- 文件清单和安装/卸载规则。
- 兼容版本要求。
- 是否需要后台运行，以及启动条件。

首次安装时可选择组件；安装后可通过 Maintenance 添加、移除或更新可选组件。依赖由维护系统解析，并在执行前展示将发生的组件变化。

组件、能力、业务领域、Provider、进程、UI 页面和 CLI 入口是不同概念，不要求一一对应。代码模块化不意味着每个模块都要独立进程；组件是否需要独立运行，应根据技术边界、资源隔离、权限需求和实际收益决定。

**未安装或未启用的功能不得启动对应后台工作。** 未启用功能不应创建常驻进程、后台轮询、定时任务或自动采集；启用后也应遵循该功能明确的运行条件。安装某组件不等于启用它，启用也不意味着必须常驻运行。

## 7. 运行架构与进程管理

### 7.1 现有架构作为基线

Zentwik 当前采用 UI + Worker 双进程架构。安装、升级和维护应以该架构为基线，不将产品改造成单进程，也不擅自改变 UI 与 Worker 的职责边界。

- **UI：** 负责界面展示、用户交互和前台操作。
- **Worker：** 负责后台工作、硬件接口、调校执行、监控数据处理及相关系统操作。
- **IPC：** UI 与 Worker 通过项目现有的本地进程间通信协议交互，沿用现有协议与管道，不另行叠加一套通信框架。

具体职责以当前代码和架构文档为准。本节不替代现有技术设计。

### 7.2 进程数量与按需启动

双进程是当前产品的基础结构，不代表未来绝对禁止其他进程。确有明确收益时，可以引入额外进程，例如独立的安装/维护入口、按需启动的 CLI，或有充分理由需要独立生命周期、权限边界或故障隔离的组件。

引入额外进程前，应说明它解决的具体问题，并评估进程常驻成本、启动开销、IPC、部署复杂度、故障处理和维护成本。若在现有 UI 或 Worker 中即可合理完成，不增加新进程。

- 不为每个功能模块、硬件 Provider 或页面单独创建进程。
- 不为抽象上的隔离而增加常驻进程或 Windows Service。
- 额外进程默认按需启动；任务完成或功能关闭后，应在适当时机退出。
- 未安装、未启用或当前不满足运行条件的功能，不启动其专属进程、采集任务或后台轮询。
- 不使用功能时，不应仅因组件已安装而持续占用 CPU、内存或唤醒系统。
- 后台进程应有明确的启动条件、停止条件、生命周期所有者和异常恢复策略，避免重复实例及孤儿进程。

### 7.3 Worker 权限与开机启动

沿用 Zentwik 既有 Worker 权限设计，不因安装体系另造权限代理层。

用户启用开机自启时，按既有设计通过 Windows 计划任务启动 Worker，并按配置请求所需的提升权限。该行为应由用户明确启用和授权；关闭开机自启时，应移除或禁用 Zentwik 对应的计划任务。

普通启动、按需提权及 Worker 的实际运行权限应按当前实现和具体操作需求处理。不要为了减少某个提示而关闭系统安全功能，也不要让无关功能被迫采用更高权限。

除非现有 UI + Worker 架构和计划任务机制无法满足已确认需求，否则不新增常驻 Broker、额外权限代理或 Windows Service。确需引入时，应作为单独架构变更论证，而非安装系统的默认组成。

## 8. 升级、修复与卸载

### 升级

- 检测版本与兼容性。
- 更新程序及所选组件。
- 必要时迁移配置格式。
- 保留用户配置、方案和历史数据。
- 升级前妥善处理 UI、Worker 及正在运行的维护任务，避免覆盖正在使用的文件。
- 按安装状态更新 Worker 和开机任务所引用的程序路径。
- 升级失败时提供恢复方式。

### 修复

- 检查程序文件完整性。
- 恢复缺失或损坏文件。
- 检查组件与依赖状态。
- 检查现有 Worker 的启动、通信和运行状态。
- 检查并修复 Zentwik 自身的计划任务及安装信息。
- 不因修复而默认安装、启用或启动用户未选择的功能。
- 输出日志。

### 卸载

- 在安全停止相关运行实例后，移除程序文件、快捷方式及 Zentwik 自身的系统集成。
- 删除 Zentwik 自身创建的计划任务及其他安装注册项。
- 默认保留用户配置和重要数据。
- 提供清理缓存及全部用户数据的选项。
- 删除个人数据前要求用户明确确认。
- 不删除其他软件共同使用的运行库或系统组件。

## 9. 数据迁移与部署模式转换

规划支持：

- Portable → Registered。
- Registered → Portable。
- Portable → 其他目录。
- 标准安装目录迁移。
- 用户数据导出、导入和恢复。

迁移前备份，迁移后校验。成功前保留原始数据，不因转换失败而丢失配置、方案和历史记录。

迁移时同步处理 Worker 路径、计划任务和其他 Zentwik 系统集成，避免迁移后仍指向旧目录。不同用户的配置、权限和计划任务不得意外混用。

## 10. 下载、校验与发布信任

当前项目不把付费代码签名证书作为发布前提，也不要求为此购买商业证书。

发布包通过 GitHub Releases 等明确渠道分发，并提供 SHA-256 校验值。下载使用 HTTPS；下载后检查文件哈希，避免文件损坏或传输内容不一致。

未进行 Authenticode 签名时，Windows 可能显示未知发布者或 SmartScreen 提示。这是未签名发布的正常限制，应在发布说明中如实说明，不采用自动关闭系统保护、添加自身 Defender 排除项或静默修改系统安全策略的方式处理。

未来如有预算和发布规模需求，再评估代码签名证书。该项不阻塞当前设计与开发。

## 11. 异常恢复与日志

考虑下载中断、权限不足、文件占用、安装中断、升级失败、数据迁移失败和用户强制终止等情况。

重要操作应尽可能具备可恢复性，避免留下无法识别的半安装状态。安装、升级、修复、组件变更和卸载均记录操作结果及失败步骤，供用户查看或导出。

运行时记录应能区分 UI、Worker 和确有必要的附加进程，便于定位启动、IPC、权限和退出问题。日志机制不应要求额外常驻进程。

## 12. CLI 与自动化部署

预留命令行维护能力：

- 静默安装。
- 指定安装目录、范围和组件。
- 静默升级。
- 修复与卸载。
- 查询安装状态。
- 输出日志。

CLI 作为按需运行的命令入口，不默认常驻。具体命令、参数及权限模型在技术设计阶段确定。

## 13. 安装界面要求

安装程序与主程序保持一致的基本视觉语言，但流程应独立、简洁。根据操作类型展示部署方式、安装位置、组件选择、环境检测、确认、进度和结果。

维护程序根据已检测到的安装状态展示可执行操作。错误提示说明发生了什么、是否影响继续操作、可采取的处理方式，以及日志位置。

## 14. 待研究与待决策事项

- 安装技术：WiX Burn、MSIX 或其他方案。
- 便携版分发：独立 ZIP 包、便携 Setup 或两者并存。
- Maintenance 的具体实现与分发方式。
- 内置更新器与 Setup 的职责边界。
- Worker 在两种部署模式下的启动、提权、计划任务配置和清理方式。
- 组件仓库、下载缓存和版本兼容策略。
- 自包含发布与系统运行库依赖的取舍。
- 多用户、多版本和多便携实例的隔离规则。
- 配置目录自定义及迁移策略。
- 确有必要时，是否存在需要独立进程的具体功能及其资源收益；不得预设新增常驻服务。

## 15. 当前结论

部署体系暂定为：

- **Registered：** 标准安装。
- **Portable：** 便携部署。
- **Zentwik Setup：** 首次安装与升级。
- **Zentwik Maintenance：** 修复、组件变更与卸载。
- **Shared Infrastructure：** 安装状态、组件清单、依赖解析、文件校验、数据迁移、日志与恢复。
- **运行架构：** 保留现有 UI + Worker 双进程结构及既有 IPC。
- **权限与自启：** 沿用现有 Worker 权限设计；用户启用开机自启时使用既有计划任务方案。
- **额外进程：** 允许在有明确技术收益时按需引入，但不默认常驻；未启用的功能不启动。

本文件记录已讨论的产品方向。技术选型和实现边界仍需结合 Zentwik Next 当前代码、发布方式及 Worker 架构进行核验。
