# 安装、部署与维护系统需求

- 状态：Proposed（产品方向草案，待结合现有实现评估）
- 日期：2026-11-26
- 涉及产品：Zentwik Next
- 文档类型：产品需求 / 架构预研

## 1. 目标

建立统一的 Windows 安装与维护体系，覆盖首次安装、升级、修复、组件变更、卸载和部署模式转换。

用户可选择标准安装或便携部署。两种模式共享产品功能、配置格式和核心实现，不维护两套产品。

## 2. 部署模式

### 2.1 标准安装（Registered）

- 支持当前用户（Per-user）和所有用户（Per-machine）安装。
- 支持自定义程序安装目录。
- 程序文件与用户配置、日志、缓存、历史数据分开存放。
- 可选创建开始菜单和桌面快捷方式。
- 可选开机启动、文件关联及协议关联。
- 注册 Windows 卸载信息，并支持独立维护程序。
- 升级时保留用户配置和数据。

### 2.2 便携部署（Portable）

- 不进行常规 Windows 安装注册，不要求注册卸载信息。
- 用户选择解压或部署目录。
- 默认将配置、日志及必要数据存放在便携数据目录。
- 支持复制、移动和多个独立实例。
- 不强制创建快捷方式、开机启动或文件关联。
- 仍可使用需要系统权限的功能；涉及提权、服务或驱动时按 Windows 权限规则处理。

便携版不应是功能阉割版。两种模式的功能差异只来自部署方式、数据位置和系统集成条件。

便携模式应通过明确的部署标识识别，不以目录名称推断。

## 3. 安装与维护入口

采用两个独立程序入口，共享安装状态、组件清单和维护基础设施。

### 3.1 Zentwik Setup

负责首次安装与升级：

- 检测已有安装及版本。
- 检查 Windows 版本、系统架构、权限和磁盘空间。
- 选择标准安装或便携部署。
- 选择安装范围和程序目录。
- 选择可选组件。
- 检测并处理运行库及外部依赖。
- 下载、安装并验证所需文件。
- 执行安装或升级并显示进度与结果。

检测到已有版本时，应识别安装位置、部署模式和组件状态，进入适当的升级或维护流程，避免盲目覆盖。

### 3.2 Zentwik Maintenance

负责已有安装的维护，且必须能够独立于主程序运行：

- 修复程序文件及安装状态。
- 添加、移除和更新可选组件。
- 修改允许变更的安装选项。
- 卸载程序及其系统集成。
- 迁移或恢复用户数据。
- 输出维护日志和诊断信息。

即使主程序、UI 或 Worker 无法启动，用户仍应能够运行 Maintenance。

### 3.3 共享基础设施

Setup 与 Maintenance 共用：

- 安装实例与版本识别。
- 组件清单及依赖解析。
- 文件完整性检查。
- 下载与校验。
- 安装状态管理。
- 操作日志。
- 数据保护、迁移与回滚机制。

两个入口可以独立分发，但不维护两套互不兼容的安装状态。

## 4. 安装位置与用户范围

### 4.1 程序与数据目录

分别管理：

- 程序文件目录。
- 用户配置目录。
- 日志目录。
- 缓存目录。
- 历史数据目录。

程序安装位置变化不应导致用户配置和历史数据丢失。数据目录是否允许自定义，作为后续设计项确认。

### 4.2 安装范围

**Per-user：** 仅为当前 Windows 用户安装，优先使用用户级目录，尽量避免不必要的管理员权限。

**Per-machine：** 为整台计算机安装，使用适当的系统级目录；需要管理员权限时明确请求。不同 Windows 用户的数据应保持隔离。

## 5. 依赖与运行环境

安装前检查实际发布所需的环境，包括：

- Windows 版本与系统架构。
- .NET Runtime（若发布方式需要）。
- Visual C++ Redistributable（若组件需要）。
- WebView2 Runtime（若 UI 技术栈需要）。
- 必要驱动、硬件接口及系统权限。
- 目标目录权限和磁盘空间。

依赖检测结果区分：已满足、缺失、版本不兼容、架构不匹配、状态无法确认、需要提权或重启。

缺少依赖时，向用户说明用途和处理方式，并提供下载与安装。优先使用依赖维护方的官方分发渠道；显示依赖名称、版本、来源和进度。已满足要求的依赖不重复安装。

支持离线安装包。离线环境缺少依赖时，明确列出所需文件及获取方式。

## 6. 组件管理

组件清单应声明：

- 唯一 ID、名称、版本和说明。
- 适用平台与安装条件。
- 依赖及冲突关系。
- 文件清单和安装/卸载规则。
- 兼容版本要求。

首次安装时可选择组件；安装后可通过 Maintenance 添加、移除或更新组件。依赖由维护系统解析，并在执行前展示将发生的组件变化。

组件、能力、业务领域、Provider、Worker/Service、UI 页面和 CLI 入口是不同概念，不要求一一对应。具体组件边界结合现有架构评估，不为拆分而拆分。

## 7. 升级、修复与卸载

### 升级

- 检测版本与兼容性。
- 更新程序及所选组件。
- 必要时迁移配置格式。
- 保留用户配置、方案和历史数据。
- 升级失败时提供恢复方式。

### 修复

- 检查程序文件完整性。
- 恢复缺失或损坏文件。
- 检查组件与依赖状态。
- 检查必要的 Worker / Service 状态。
- 修复安装信息并输出日志。

### 卸载

- 移除程序文件、快捷方式及 Zentwik 自身的系统集成。
- 默认保留用户配置和重要数据。
- 提供清理缓存及全部用户数据的选项。
- 删除个人数据前要求用户明确确认。
- 不删除其他软件共同使用的运行库或系统组件。

## 8. 数据迁移与部署模式转换

规划支持：

- Portable → Registered。
- Registered → Portable。
- Portable → 其他目录。
- 标准安装目录迁移。
- 用户数据导出、导入和恢复。

迁移前备份，迁移后校验。成功前保留原始数据，不因转换失败而丢失配置、方案和历史记录。

## 9. 下载、校验与发布信任

当前项目不把付费代码签名证书作为发布前提，也不要求为此购买商业证书。

发布包通过 GitHub Releases 等明确渠道分发，并提供 SHA-256 校验值。下载使用 HTTPS；下载后检查文件哈希，避免文件损坏或传输内容不一致。

未进行 Authenticode 签名时，Windows 可能显示未知发布者或 SmartScreen 提示。这是未签名发布的正常限制，应在发布说明中如实说明，不采用绕过系统安全提示的方式。

未来如有预算和发布规模需求，再评估代码签名证书。该项不阻塞当前设计与开发。

## 10. 异常恢复与日志

考虑下载中断、权限不足、文件占用、安装中断、升级失败、数据迁移失败和用户强制终止等情况。

重要操作应尽可能具备可恢复性，避免留下无法识别的半安装状态。安装、升级、修复、组件变更和卸载均记录操作结果及失败步骤，供用户查看或导出。

## 11. CLI 与自动化部署

预留命令行维护能力：

- 静默安装。
- 指定安装目录、范围和组件。
- 静默升级。
- 修复与卸载。
- 查询安装状态。
- 输出日志。

具体命令、参数及权限模型在技术设计阶段确定。

## 12. 安装界面要求

安装程序与主程序保持一致的基本视觉语言，但流程应独立、简洁。根据操作类型展示部署方式、安装位置、组件选择、环境检测、确认、进度和结果。

维护程序根据已检测到的安装状态展示可执行操作。错误提示说明发生了什么、是否影响继续操作、可采取的处理方式，以及日志位置。

## 13. 待研究与待决策事项

- 安装技术：WiX Burn、MSIX 或其他方案。
- 便携版分发：独立 ZIP 包、便携 Setup 或两者并存。
- Maintenance 的具体实现与分发方式。
- 内置更新器与 Setup 的职责边界。
- Worker / Service 在两种部署模式下的安装、提权和清理方式。
- 组件仓库、下载缓存和版本兼容策略。
- 自包含发布与系统运行库依赖的取舍。
- 多用户、多版本和多便携实例的隔离规则。
- 配置目录自定义及迁移策略。

## 14. 当前结论

部署体系暂定为：

- **Registered：** 标准安装。
- **Portable：** 便携部署。
- **Zentwik Setup：** 首次安装与升级。
- **Zentwik Maintenance：** 修复、组件变更与卸载。
- **Shared Infrastructure：** 安装状态、组件清单、依赖解析、文件校验、数据迁移、日志与恢复。

本文件记录已讨论的产品方向。技术选型和实现边界仍需结合 Zentwik Next 当前代码、发布方式及 Worker 架构进行核验。
