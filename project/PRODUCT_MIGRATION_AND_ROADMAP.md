## 0. 总体决策

### 0.1 产品方向

Zentwik Next 不是从零开始的新产品。旧版 Zentwik 已经实现了大量真实用户功能和业务流程；新版的任务是在更可靠的架构上继承这些产品能力，并在明确的缺陷处改进。

因此，开发目标定义为：

> **以旧版已实现的用户能力和行为作为迁移基线，以新版架构作为承载方式；保留有效行为，修正有证据的缺陷，并为产品简报明确提出的未来能力预留稳定扩展位置。**

不得把旧版代码的技术债等同于旧版功能的价值，也不得把新版已经存在的抽象、Provider 或数据类型误判为产品功能已经完成。

### 0.2 三条同时成立的要求

1. **产品连续性**：旧版用户已经能完成的有效操作，新版原则上必须继续支持。任何删减、改变默认行为或改变操作语义，都必须记录理由并得到明确决策。
2. **架构演进**：旧版 IPC、巨型分派、权限边界、状态所有权和场景恢复等缺陷不照搬。迁移的是行为与业务规则，不是旧架构。
3. **未来可扩展性**：新版必须为产品简报中明确规划的能力预留正确的领域边界、契约位置、数据兼容策略和生命周期接口；但不得为了遥远的可能性提前实现复杂框架。

### 0.3 不能再采用的开发方式

- 不以“新版当前缺少什么”作为唯一需求来源，忽略旧版已有功能。
- 不把 Provider、接口、模型、能力 ID 或 CLI 命令存在，直接算作用户功能完成。
- 不将旧版成熟功能拆成一堆互不闭环的小任务，长期停留在“底层能力已具备”。
- 不为追求架构整齐而重写已经正确、独立且可复用的实现。
- 不在没有行为差异说明的情况下，悄悄改变旧版功能表现。
- 不先建设完整插件市场、复杂规则编辑器、历史数据库或 GUI，再回头补核心功能。
- 不重复进行全仓库盘点、架构重审和大型安全审计；只针对具体迁移任务研究相关代码。
- 不把已有旧版盘点重新誊写成第二份文档；迁移映射只记录新版差异，并随领域开发增量维护。
- 不因真机验证尚未完成而停止独立的软件功能开发；也不得用 fake 测试替代硬件行为证据。

## 1. 迁移原则与完成定义

### 1.1 迁移对象分层

每项功能都必须区分以下四层：

| 层次 | 迁移内容 | 例子 |
|---|---|---|
| 用户能力 | 用户能执行的操作和可观察结果 | 创建电源方案、编辑 AC/DC 策略、应用并看到结果 |
| 业务行为 | 规则、状态转换、匹配、优先级、失败和恢复语义 | 进程启动后匹配规则、失败重试、PID 复用识别 |
| 平台实现 | Win32、SMU、MSR、CPU Sets、电源 API、传感器接口 | `PowerReadACValueIndex`、PawnIO、处理器组 API |
| 产品交互 | CLI、未来 GUI、诊断信息、设置和本地化 | 命令参数、交互提示、错误详情、用户自建名称 |

平台实现迁移成功，不代表用户能力迁移成功。

### 1.2 每项旧版能力的迁移分类

迁移表使用以下状态，不得只使用“完成/未完成”：

- **未迁移**：新版尚无对应实现。
- **底层已具备**：存在 Provider/API/模型，但缺少完整业务链。
- **部分迁移**：主要流程存在，仍缺旧版已有行为或关键状态。
- **行为等价**：新版已覆盖旧版原有有效行为，操作结果和边界基本一致。
- **改进迁移**：保留原有有效行为，并修正已确认缺陷。
- **新增能力**：旧版没有，由新版产品规划新增。
- **有意不迁移**：因安全、平台限制、维护成本或产品决策而不保留；必须写明原因、替代方式和用户影响。

“行为等价”不要求代码结构相同，也不要求沿用旧版缺陷。

### 1.3 功能完成的最低标准

一项功能只有在以下相关部分全部完成后，才能标记为“行为等价”或“改进迁移”：

1. 用户可通过正式入口配置和执行该功能。
2. 领域模型能表达实际需要的参数和状态，不丢失旧版有效选项。
3. 平台调用链真实接通，不是只有接口或假实现。
4. 读取、写入、回读、失败反馈和必要恢复闭环完整。
5. 持续性行为（进程生命周期、开机、休眠恢复等）按该功能要求工作。
6. 配置保存、加载、迁移和版本兼容有明确行为。
7. CLI 已提供相应用户操作；未来 GUI 可消费同一业务契约。
8. 文案能区分成功、部分成功、跳过、不支持、权限不足和真实失败。
9. 有与本次修改直接相关的测试或实际验证证据。
10. 迁移差异和仍未验证的硬件条件如实记录。

不要求每个功能在所有硬件上都能验证；没有对应硬件时，应使用 fake/provider 测试验证业务闭环，并将真实硬件验证明确标为未验证。

软件实现状态与硬件验证状态必须分开记录。fake Provider 通过只能证明软件调用链、业务规则和错误语义，不证明硬件接受写入、拓扑映射正确或休眠恢复有效。涉及硬件行为的条目，在对应管理员会话真机验证完成前，不得标记为“行为等价”或“改进迁移”；应标记为“软件实现完成，待真机验证”或等价的独立状态。

## 2. 目标架构与未来扩展边界
本节是功能演进必须遵守的边界，不要求为所有未来功能立即增加实现。

### 2.1 三种独立方案

必须长期保持三个独立领域对象及生命周期：

- **CPU Tuning Plan**：CPU 平台调校参数、基线引用、应用结果。
- **Power Plan**：Windows 电源计划引用、策略参数和 Zentwik 扩展参数。
- **Scheduling Plan**：进程匹配规则、目标处理器集合、优先级和持续执行策略。

场景是协调器，不是第四种方案。场景可以引用一个或多个领域方案，也可以只执行单一领域动作。

三个方案必须可以独立创建、编辑、复制、重命名、删除、查看、应用和恢复。某个平台不支持某项能力，不应使其他方案失效。

### 2.2 配置、目标、当前值与恢复基线

涉及系统修改的领域，只需明确区分：

- **配置值**：用户保存的方案内容。
- **目标值**：当前方案或自动化准备应用的值，可在执行时计算，不要求重复保存一份长期状态。
- **当前值**：最近从系统或硬件读取到的实际值，并记录必要的采样时间。
- **恢复基线**：用于恢复的值及其来源。

不得把“配置已保存”显示成“硬件已应用”，不得把请求值当成实际值，也不得把运行时采样值自动认定为出厂基线。

硬件基线记录硬件身份、采集来源、采集时间和适用范围即可。只有确实影响安全恢复的场景才增加可信等级等细分元数据。

### 2.3 Provider 与领域模型

- 领域模型表达用户意图和跨平台语义。
- Platform Provider 负责平台差异、探测、读写、回读和错误映射。
- 一个领域可拥有多个 Provider；一个 Provider 可提供多个能力。
- 能力探测必须反映真实运行状态，不能只根据模块注册或驱动文件存在就报告可用。
- Provider 不应把某一硬件平台的寄存器、GUID 或厂商枚举泄漏成通用产品语义。
- 新增参数时优先扩展已有领域模型，不为每个平台复制一套完整方案系统。

### 2.4 模块、插件和能力

当前只要求保持清楚的模块边界，不提前建设完整插件管理系统：

- 内置模块具有稳定 ID 和明确职责。
- 模块是否可用、是否启用、运行是否正常，按实际需要分别表达；不要把安装、加载、运行和健康状况硬塞进一个复杂状态枚举。
- 缺少某模块不得导致无关领域不可用。
- 第三方插件未来默认采用独立进程和受控 IPC，不直接获得 LocalSystem 权限或直接访问硬件驱动。
- 内部模块 API 不自动成为第三方稳定 API。插件 API 的权限、版本和故障隔离在真正启动插件项目时再设计。
- 插件市场、在线分发和自动更新不是当前核心功能的前置条件。

当前不实现通用插件框架、热加载、复杂依赖解析或完整模块生命周期管理。

### 2.5 自动化与状态所有权

场景引擎负责协调，不拥有 CPU、Power、Scheduling 的领域数据。StateLedger 负责必要的字段所有权、恢复信息和操作结果，不扩展成通用审计数据库。

必须遵守：

1. 用户明确发起的 Zentwik 操作优先执行，不得被自动化所有权检查无故阻止。
2. 用户通过 Zentwik 修改方案时，先保存配置；用户选择应用后，再走正常应用链路并更新账本。
3. 用户通过 Zentwik 直接修改运行中的字段时，按明确操作立即执行。需要持续脱离自动化控制时，用户可选择接管该字段；普通修改不应自动造成永久接管。
4. Zentwik 自己发起的写入必须在内部记录操作来源和目标值，不能被监控线程误判为外部修改。
5. 对于 Zentwik 之外发生的变化，只判断为“外部修改”；无法可靠获知来源时，不猜测是用户、任务管理器还是其他应用。
6. 提供简单的全局外部修改策略：
   - **尊重外部修改**（默认）：检测到外部变化后，暂停自动覆盖受影响字段。
   - **自动化优先**：只要自动化仍拥有该字段，就允许按当前方案重新应用。
7. 用户明确接管的字段始终不被自动化覆盖，直到用户主动释放接管；全局策略不能绕过这一点。
8. 所有权按字段处理，一个字段发生冲突不得阻断同一对象的其他字段。
9. 自动化退出时不得无条件写回过期快照；仅恢复仍由该自动化持有且未被用户接管的字段。
10. 不同领域可以分别仲裁；同一事件重复到达必须幂等，避免反复写入。

不要求识别所有外部修改者，也不建立复杂的来源追踪状态机。

### 2.6 实时监控与历史数据

实时监控先满足真实采样和稳定呈现：

- 采样源不依赖 UI 是否打开。
- 样本包含指标、值、单位、时间戳和有效性；确有必要时再记录来源细节。
- 采样频率与 UI 刷新频率分离。
- 数据过期时明确显示，不把旧样本冒充实时值。
- 不支持的传感器报告 unavailable，不用估算值冒充实测值。
- 基础订阅、取消和慢客户端保护在实时数据链路需要时实现，不提前建设通用遥测平台。

先完成实时监控和关键状态展示。复杂背压体系、历史数据库、长期趋势、区间统计和导出按实际需求后续实施。

### 2.7 国际化、主题与用户配置

从当前产品入口开始保持资源化：

- 首批语言 zh-CN、zh-TW、en-US。
- 支持运行时切换和回退。
- 内部 ID、协议枚举和配置键不随语言改变。
- 用户自建方案名、规则名、进程名和备注不翻译、不重写。
- 强调色必须保留用户自定义能力，不得锁定产品默认色。
- 主题、信息密度、缩放和动效设置由产品配置管理，不散落在 UI 私有状态中。

### 2.8 数据与兼容

- 设置、方案、场景、模块元数据、硬件基线、执行历史、监控历史分别定义数据责任。
- 配置必须有 schema/version 和迁移策略。
- 迁移失败不得静默清空用户配置。
- 新版本读取旧配置时要明确保留、转换或拒绝的字段。
- 方案 ID、能力 ID 和内部枚举保持稳定；展示文本可本地化。
- 用户降级或卸载时，必须明确硬件参数、驱动、服务和配置如何处理。
- 不把所有数据塞入一个总 JSON，也不为了“未来可能”提前引入大型数据库。

## 3. 旧版功能迁移路线

旧版基线：`Motu-Z/Zentwik` 的旧版 `main`，提交 `bc3c59b`，版本 `2.6.0-can16`。具体类与方法以 `research/01-legacy-inventory.md` 为索引，实施前再读取对应源码，不凭盘点文档盲目搬运。

### 3.1 CPU 调校：AMD 与 Intel 统一工作流

**旧版已有能力**

- AMD 逐核 Curve Optimizer，范围和逐核参数。
- AMD FMax 上限设置。该能力按具体平台与固件探测，不预设所有 AMD 笔记本均可写入；用户的 Ryzen 9 9955HX 当前 BIOS/AGESA 环境下，相关 OC/FMax 通道受限，不能列为该设备的可用能力。
- 调校快照、写入回读、防砖护栏。
- 启动应用与休眠恢复补写。
- Intel Core/GPU/Cache 电压偏移。
- Intel 8 档倍频上限、逐项回读和恢复基线。

**新版目标**

一个统一 CPU Tuning Plan 工作流，平台 Provider 提供不同能力。AMD 和 Intel 不应复制两套方案存储、应用状态和 CLI 框架。FMax 是独立于硬件功耗墙的 CPU 调校能力，必须按具体平台探测结果决定是否提供，不作为所有 AMD 设备均可用的迁移承诺。

**迁移任务**

1. 对照旧版 `SmuReader`、`TuningApplyService`、`BootGuard`、`SleepResumeWatcher`，核对新版 AMD CO 从探测、逐核寻址、读取、编辑、写入、回读到恢复的完整链。
2. 保留新版 A1 已完成的数值掩码编码和拓扑映射，不重复实现 A1。真机逐核只读交叉验证与受控写入作为硬件验收，不阻塞其他 CPU 工作。
3. 完成 CO 范围分层、平台范围报告和逐核错误表现；不把未确认的固件限制写成确定事实。
4. 对 FMax 按平台能力实施读取、写入、回读和失败处理，并接入 CPU Tuning Plan；能力探测不通过或固件拒绝时，明确报告不支持/不可用，不得强行写入。9955HX 当前 BIOS/AGESA 下已知相关通道受限，此结论仅适用于已验证设备与固件环境。
5. 将新版 Intel 写入路径接入 Contracts、Agent 和 CPU Tuning Plan，覆盖 Core/GPU/Cache 电压域及倍频档位；明确哪些 Intel 平台支持、哪些仅可读取。
6. 让 Intel 方案具备保存、应用、回读、恢复和启动策略；持久化能力必须按平台实际支持情况标记，不能假定旧版会话级功能天然支持重启重放。
7. 对照旧版逐项保留防砖、启动应用、休眠恢复行为，并利用新版基线和账本改善状态判断。
8. CLI 同步提供能力查看、基线查看、方案编辑、应用、恢复和结果明细。
9. 旧版 CPU 硬件功耗限制（AMD PPT/TDC/EDC、STAPM/FAST/SLOW，Intel PL1/PL2/Tau）已完成历史与技术调查，决定不迁移、不列入近期或未来扩展路线，也不为其预留通用 Provider 写入抽象。调查依据与平台限制见 `LEGACY_POWER_CONTROL_INVESTIGATION.md`。

现有证据还支持一项产品层面的工程推定：笔记本 HX 平台不应默认具备通过通用 SMU Mailbox 直接修改功耗墙的能力；这条路径在笔记本固件上通常不可依赖，功耗管理更可能由厂商 EC/GCU 或其他专有控制链路承担。同方系目前已有的 GCU/MQTT 线索也指向厂商控制路径。但现有直接写入失败证据主要来自一台 9955HX，EC/GCU 侧尚无完整寄存器、协议和写入验证，因此不能表述为“所有 HX 绝对不能通过 SMU 写功耗”或“所有机型只能走 EC”。这项推定用于确定产品默认策略：不实现通用 HX SMU 功耗墙写入，也不把 EC 控制列为当前开发任务；未来只有具体型号具备可验证的厂商接口、安全回滚和真机证据时才单独评估。

**完成标准**

用户能够通过 CLI 创建/编辑 AMD 或 Intel CPU 调校方案，查看当前值和基线，应用后看到真实回读值，识别部分成功和失败，并按明确策略恢复。无真实硬件时，fake 测试覆盖完整工作流；硬件验证状态单独标注。

### 3.2 Power：恢复完整的电源方案管理

**旧版已有能力**

- Windows 操作系统电源方案枚举、切换、派生新建、改名、删除。
- 内置方案保护。
- AC/DC 策略参数读写。
- EPP、Boost、最大/最小处理器状态、散热方式、核心停泊下限、空闲禁用、ASPM 等策略。
- 逐项支持状态、错误信息和写后重新激活。

**新版目标**

Power Plan 专指 Windows 操作系统电源计划与其策略设置，不包含 CPU 硬件功耗墙（PPT、STAPM、PL1/PL2 等）控制。它不只是 GUID 包装，应区分系统电源方案、方案设置、当前 AC/DC 值、用户定义值和实际生效状态。

**迁移任务**

1. 逐项对照旧版 `PowerPolicyApi`、`PowerPolicyService`、`PowerSchemePreset`，建立旧版策略项到新版领域模型的映射。
2. 实现电源方案枚举、详情、当前活动方案、切换、复制/派生、重命名、删除；保护系统内置方案。
3. 实现电源设置子组与设置项发现，保留 GUID、单位、友好名称、范围、枚举选项和硬件支持状态。
4. 对 AC/DC 分别读取和设置值，避免把当前电源状态与用户保存值混为一谈。
5. 完成逐项应用、逐项结果、回读验证、部分失败报告和可行的回滚。
6. 处理计划切换与策略写入之间的失败关系；不能只返回整体失败而留下未说明的部分状态。
7. 建立可扩展的设置元数据，不将所有 GUID 和文案硬编码在 CLI。
8. CLI 提供独立 `power` 命令组，至少覆盖 schemes、settings、active、create/duplicate、rename、delete、set/apply、restore 和 JSON 输出。
9. 用户自定义方案名与 Windows 内置名称应正确显示；国际化只处理产品生成的文案。

**完成标准**

用户可以仅通过 CLI 完成旧版已经支持的电源方案和策略操作，查看每项 AC/DC 值及支持状态，修改后回读确认；部分失败不会被伪装为成功。

### 3.3 Scheduling：从一次性写入恢复为完整进程调度系统

**旧版已有能力**

- 按进程名匹配规则。
- CPU Sets 或 Affinity Mask。
- 优先级设置，包含 EcoQoS，不包含 RealTime。
- 持续扫描、失败重试、漂移探测、PID 复用识别和解绑。
- 自定义掩码集合与格式化/解析。
- 进程实例信息和目标状态管理。

**新版目标**

Scheduling Plan 是可持续执行的进程策略集合，不是一次性对 PID 调用 SetAffinity。

**迁移任务**

1. 对照旧版 `ProcessWatcher`、`CpuSetScheduler`、`ProcessPriority`、`MaskBinding` 和相关 ledger，提取需要保留的有效行为。
2. 首先完整迁移旧版按进程名匹配；正确识别进程实例，处理 PID 复用。路径、包身份、签名、用户范围和父子进程匹配暂不建立通用框架，出现明确需求后再扩展。
3. 完成 CPU Affinity 和 CPU Sets 两种执行方式，并明确各自适用条件和限制。
4. 正确表达处理器组和跨组目标；不能让 128 位领域掩码最终悄悄收敛为单个 ulong。
5. 完成旧版已有优先级和 EcoQoS；RealTime 继续不作为普通预设，除非另有明确产品决策。
6. 实现进程启动、退出、重启、PID 复用、规则更新和服务恢复后的持续应用。
7. 实现必要的失败重试、漂移检测和恢复/解绑；诊断中显示最后执行结果和失败原因，不预建复杂规则引擎。
8. 将字段级所有权融入 StateLedger；一个字段被拒绝时，不得连带写入该字段。
9. 自定义掩码支持保存、编辑、删除、查看使用位置和格式化。
10. CLI 以职责清晰为准：`processes` 用于进程查看，`scheduling` 用于规则和调度操作；拓扑信息优先作为能力/诊断信息提供，只有确有独立工作流时才增加单独命令。
11. 对规则匹配提供必要解释，例如匹配了哪条规则、应用了什么目标、哪些字段因平台不支持而跳过。
**完成标准**

用户创建规则后，目标进程启动即可自动应用；进程持续运行时策略可被维持；进程退出、重启和 PID 复用不会造成错误操作；用户接管后自动化不会覆盖。旧版已有的掩码和优先级能力可以通过 CLI 使用。

### 3.4 Automation / Scenes：继承触发能力，简化规则系统

**旧版已有能力**

- 进程运行、进程退出、电池、交流供电四种触发。
- 规则优先级和防抖。
- 一条规则可引用调校、调度和电源方案。
- 场景启停和状态查看。

**必须修正的旧版缺陷**

- 规则无命中时不恢复。
- 退出后调校和电源值可能长期残留。
- 一条规则同时决定三个领域，无法按领域独立仲裁。
- 缺少可靠的用户操作保护和字段级恢复。

**新版目标**

场景负责根据事件启用或退出一个或多个领域方案。保持触发条件与执行动作边界清楚，但不提前建设通用规则引擎。

**迁移任务**

1. 保留旧版四种触发器及已有配置迁移能力。
2. 第一阶段支持进程启动/退出和 AC/DC 状态变化。
3. 保留必要的规则优先级和防抖。
4. CPU、Power、Scheduling 分别仲裁，允许场景只控制一个领域。
5. 通过 StateLedger 记录应用所需的前值、目标值、实际回读值和恢复资格。
6. 区分 Zentwik 内部写入与外部修改。外部修改按全局策略处理；无法确认来源时不推断操作者身份。
7. 用户通过 Zentwik 修改时正常保存或应用；用户明确接管的字段不被自动化覆盖。自动化退出时只恢复仍由它控制的字段。
8. 正确处理进程退出、规则禁用和服务重启等当前实际支持的生命周期。
9. 提供必要的场景状态和最近执行结果，复杂执行历史与命中分析后续按需求增加。

**后续扩展**

时间窗口、CPU/GPU 负载阈值、AND/OR 组合条件、复杂滞回、冷却策略、场景模板和可视化规则编辑器均不属于首轮迁移要求。需要具体用户场景时再逐项增加。

**完成标准**

旧版已有触发场景能够迁移或通过 CLI 重建；新版能正确处理独立领域动作、冲突、退出恢复和用户接管。不得以“场景引擎类存在”作为完成依据。

### 3.5 Monitoring：先完成可靠的实时状态

**旧版已有能力**

- 进程 PID、映像名、路径、CPU 占用、优先级。
- CO/FMax 快照。
- AC/DC 状态。
- 简单日志和诊断信息。

**新版首轮需要实现的能力**

- CPU：总负载、逐核负载，以及平台能够真实提供的频率、温度和功耗。
- GPU：负载、频率、温度和功耗，按实际 Provider 能力提供。
- 内存：使用量。
- 进程：CPU、内存、优先级、调度目标和实际状态。
- 电源、活动方案、场景和调度状态。

磁盘 I/O、网络 I/O 可在有可靠采样源时纳入后续增量，不阻塞首轮核心监控。

**迁移与实现任务**

1. 保留旧版进程监控的基本信息和用户可见字段。
2. 样本至少包含指标、值、单位、时间戳和有效性。
3. 为 CPU/GPU/内存建立可用的采样源；平台不支持时报告 unavailable。
4. 采样频率与 UI 刷新频率分离。
5. 显示数据年龄和过期状态，不能把旧样本显示成实时值。
6. 进程监控与 Scheduling 状态关联，展示规则目标和当前实际值。
7. 将活动方案和场景状态纳入监控概览。
8. CLI 的 `monitor` 支持必要的指标筛选、采样间隔、JSON 输出和取消订阅。

**后续扩展**

磁盘/网络 I/O、复杂背压和多客户端订阅、历史数据库、趋势、区间统计和导出按实际需求实施，不作为首轮实时监控的前置条件。

**完成标准**

核心指标有真实采样来源和时间戳；不支持的指标不会伪造；UI 关闭或客户端变慢不会拖垮服务。历史存储不作为实时监控完成的前置条件。

### 3.6 系统设置、诊断与托盘

**旧版已有能力**

- 主题、系统强调色和自定义强调色。
- 窗口材质、动效。
- 自启动形态、登录延迟、启动调校、关闭行为。
- 监听进程、错误通知、Toast 时长、防砖和休眠感知。
- 日志、自检、导出和托盘菜单。

**迁移任务**

1. 逐项核对旧版设置的用户价值和新版归属，避免只保留少量通用开关。
2. 将设置写入责任收拢到明确的配置服务，避免 UI/Agent 双写同一配置。
3. 保留自定义强调色，不锁死默认主题或品牌色。
4. 实现设置导入、导出、版本迁移和重置；重置前说明影响范围。
5. 保留日志环形缓冲、按日落盘、留存、清理、导出和自检能力。6. 增加结构化操作记录：请求 ID、发起者、目标、请求值、实际值、失败步骤和恢复结果。
7. 诊断信息需避免不必要地记录用户路径、进程命令行等敏感数据。
8. 托盘、自启动和启动应用策略放在服务/用户会话生命周期明确后实施，不允许 SYSTEM 服务直接在错误会话创建 UI。
9. CLI 提供 settings、logs、doctor 等命令，支持机器可读输出。

**完成标准**

旧版主要设置和诊断操作在新版有明确归属与替代入口；配置迁移不会静默丢失；服务权限与用户会话边界清楚。

### 3.7 安装、升级、卸载与系统生命周期

这是正式交付能力，不应早于核心功能开发，但其中的服务连接与身份验证存在 P0 前置项，不能整体推迟到 P3。P3 负责完整安装、升级、卸载和生命周期交付；P0 先修复当前已暴露的 Agent/CLI 连接阻塞。

任务包括：

- PawnIO 驱动及模块文件的安装、版本、签名、权限和卸载策略。分发前必须核实具体组件许可证及例外条款、版本兼容性和再分发义务，不得仅凭仓库主页的许可证标签作结论。
- APOB 读取路径的产品决策：当前 PawnIO 官方模块集没有可直接读取物理内存的模块，不得假设可通过现有 PawnIO 接口直接获取 APOB。需比较外部 dump 注入、受控外部读取工具及以 Windows/CPUID/缓存拓扑为主的方案，记录安全性、可维护性和证据边界；在决策前禁止把替代拓扑来源宣称为与 APOB 完全等价。
- Agent 服务安装、升级、停止、恢复、失败动作和日志。
- 用户会话通信和命名管道身份验证。
- 休眠/唤醒、重启、服务崩溃后的状态复核。
- 配置和方案迁移、升级回滚。
- 卸载时提示并处理仍处于自定义状态的硬件参数。
- 保留或删除用户配置由用户明确选择。
- 安装包、便携包、精简包的能力差异清楚。
- 不能在卸载时无提示地留下硬件调校值，也不能在没有可靠基线时盲目写回。

## 4. 新版新增能力与未来预留

以下内容不是旧版迁移任务。它们来自产品简报、架构约束或合理的后续产品方向。必须区分“现在需要设计位置”和“现在就要实现”。

| 能力 | 价值与方向 | 当前预留要求 | 实施时机 |
|---|---|---|---|
| Intel 完整方案持久化 | 将旧版会话级 Intel 调校提升为统一方案能力 | CPU Tuning Plan 允许平台专属参数、能力声明和持久化策略 | CPU 迁移阶段 |
| GPU 调校 | 未来可能覆盖 GPU 电压、频率、功耗和风扇 | 预留独立 GPU Tuning 域或明确的扩展领域，不把 GPU 参数塞入 CPU Tuning Plan；监控先行 | GPU 监控后再立项 |
| 更丰富的处理器拓扑 | 支持多处理器组、异构核、CCD/CCX、CPU Sets | 拓扑模型应表达组、逻辑处理器、物理核心、缓存域和平台来源 | Scheduling 迁移阶段 |
| 进程高级匹配 | 路径、包身份、签名、用户/会话、父子进程等 | 当前只保留可扩展空间，不建立通用匹配器 | 出现明确用户需求后 |
| 高级场景规则 | 时间窗口、负载阈值、组合条件、冷却和滞回 | 先完成旧版触发器、优先级和防抖；高级规则按需求增加 | 基础场景稳定后 |
| 场景模板 | 分享常用游戏、工作负载和电源策略配置 | 模板与用户实例分离；导入前显示差异，不覆盖用户数据 | 场景成熟后 |
| 监控历史 | 长期趋势、区间统计、对比、导出 | 实时采样与历史存储分层，样本 schema 可演进 | 实时监控稳定后 |
| 告警与自动响应 | 温度、功耗、异常状态告警及可选自动动作 | 告警与自动化动作分离，动作仍受所有权和优先级约束 | 监控和场景稳定后 |
| 模块扩展 | 内置/官方模块按需启用 | 稳定 ID、清晰职责、基本可用/启用/运行状态 | 出现实际模块扩展需求后 |
| 第三方插件 | 外部开发者扩展能力 | 当前只保留进程隔离和权限边界原则，完整协议另行立项 | 插件项目启动时 |
| 插件发现/分发 | 安装、更新和管理扩展 | 不将市场和在线分发绑定到插件运行时 | 更后期 |
| 跨平台 | 其他操作系统上的部分能力 | 每项能力声明平台支持矩阵；Windows 核心能力不因抽象而退化 | Windows 产品成熟后 |
| 配置同步/备份 | 迁移设备或恢复配置 | 方案、设置、基线、设备绑定信息分离；硬件基线不能跨设备直接复用 | 交付能力稳定后 |
| 远程管理 | 管理其他设备 | 身份认证、授权、传输安全、设备信任和审计独立设计 | 暂不进入当前路线 |
| 脚本/自动化 API | 高级用户编排 | 对外 API 与内部接口分离，权限和执行结果可审计 | 插件/自动化成熟后 |

### 4.1 预留的边界

预留不是提前建立空壳项目。只有当前实现会妨碍一项明确的未来能力时，才调整接口或数据模型。

例如：

- CPU 与 GPU 调校现在就应分属清楚的领域；不需要现在实现 GPU 超频。
- Provider 暴露当前功能确实需要的读、写和回读能力；不要求预先设计覆盖所有厂商的通用能力元数据系统。
- 场景保留触发与动作的清晰边界；不需要现在实现通用规则引擎。
- 内部模块保持稳定 ID 和职责边界；不需要现在支持第三方插件热加载或完整依赖管理。
- 监控样本现在就应有时间戳、单位和有效性；不需要现在建设遥测平台或历史数据库。
- 进程规则先完整支持旧版进程名匹配，并正确识别进程实例；高级身份匹配按需求增加。

未来扩展点只记录必要约束，不以“预留”为由增加当前没有使用者的抽象。

### 4.2 明确暂不做

在核心迁移完成前，不投入以下工作：

- 插件市场、在线插件分发和完整第三方开发者门户。
- 远程设备管理和云端账号体系。
- 跨平台全面移植。
- GPU 超频完整工作流。
- 复杂脚本语言或任意代码执行。
- 监控历史大数据平台。
- 复杂仪表盘编辑器和可视化规则编程器。
- 与当前功能无关的微服务拆分。

这些项目不从架构上封死，但不能抢占当前产品迁移资源。

## 5. 执行顺序与里程碑

这里的里程碑按可交付能力划分，不按底层项目数量划分。一个里程碑允许多个领域并行开发，但必须有可见的产品结果。

### P0：连接阻塞、正确性修复与迁移跟踪

**目标**：恢复最小真机产品链路，修复已知状态正确性缺陷，并建立轻量、可持续更新的迁移映射。P0 不得演变成重新盘点或文档工程。

任务按以下顺序推进，可在文件边界清晰时并行：

1. **P0-A：修复 B1 服务与 IPC 连接问题。** 针对当前已安装 `ZentwikAgent` 与中完整性 CLI 连接被拒、`PipeIdentity.ReadServerSid` 返回 null 的现象，先确认运行中的服务二进制路径、服务身份、管道 ACL、服务端 SID 获取和客户端身份校验链。修复根因并重新安装/更新实际服务，完成管理员 CLI 到 LocalSystem Agent 的最小真实握手、状态读取和错误路径验证。不要仅通过 fake 或本地单元测试宣布 B1 完成。
2. **P0-B：修复 `PlanCoordinator` 两项正确性缺陷。** `ApplyPower` 前值读取失败不得继续写入；活动电源计划切换失败必须正确反映，不能吞掉失败。`ApplyScheduling` 必须分别判断字段所有权，只写入获准字段，拒绝字段不得传给底层写入。添加直接相关测试，不借机重构整个协调器。
3. **P0-C：建立轻量逐功能迁移映射。** 直接以 `research/01-legacy-inventory.md` 为索引，不重写旧版盘点。表格只记录功能、旧版入口/核心类、新版目标位置、差异/待办、软件实现状态和真机验证状态。首轮只需覆盖当前要开发的领域；随着 CPU、Power、Scheduling 等任务推进增量补齐，不得成为 P1 的整体前置关卡。
4. **P0-D：明确硬件验证边界。** 为 A1 拓扑映射、CO 掩码、仍保留的调校能力（包括按平台探测的 FMax）及休眠唤醒恢复分别记录证据、验证环境和未验证项。SMU 写入验证只针对仍保留且有明确产品需求的调校能力；已排除的硬件功耗墙写入不属于真机验证任务。fake 测试通过不等于硬件验证通过。真实逐核写入必须以映射可信和受控验证为前提；这些硬件验证不得阻塞独立的 Intel、Power、Scheduling 软件开发。
5. **P0-E：形成 PawnIO 与 APOB 决策记录。** 核实 PawnIO 具体版本、组件许可证/例外、分发义务、签名和兼容性；明确当前 APOB 不可由现有官方模块直接读取的事实，比较可行替代路径及其证据限制。该决策不阻塞其他领域开发，但在决策和验证完成前不得宣称拓扑等价或完成正式驱动分发方案。

**退出条件**
- B1 已在当前真实安装环境完成管理员 CLI 到 LocalSystem Agent 的握手与状态读取。
- 两项协调器缺陷已修复并有对应测试。
- 轻量映射表已建立并随开发维护，不要求首轮穷尽所有细项。
- 硬件验证状态与软件实现状态分开记录。
- PawnIO/APOB 的关键未知项、决策责任和后续验证条件已明确记录。
- 不重新设计已经稳定的 Contracts、Agent 或 StateLedger。

### P1：恢复三种核心方案的产品能力

**目标**：用户通过正式 CLI 能够完成旧版的主要调校、电源和调度工作流。

并行工作流：

- CPU：AMD CO、按平台能力提供的 FMax，以及 Intel 调校统一方案；FMax 不作为全平台必备能力。
- Power：电源方案 CRUD + 设置发现 + AC/DC 参数。
- Scheduling：规则、进程生命周期、CPU Sets/Affinity、优先级和持续 enforce。
- CLI：由每个领域在自身实现中同步完成，不另设最后统一补命令的阶段。

**协作边界**

- DS 作为主集成者，负责共享 Domain、Contracts、Agent、PlanCoordinator 和 CLI 主入口。
- 隔离的 Platform Provider 可以并行开发，但必须事先声明文件所有权。
- 多个 Agent 不得同时修改同一共享文件。
- 领域之间通过已确认的契约协作，不通过复制实现或直接引用彼此内部类。
- 不因某一台设备缺少真实硬件而阻塞其他领域的实现。

**退出条件**

- 三种方案均可通过 CLI 创建、查看、编辑、应用和恢复。
- 旧版核心能力逐项达到“行为等价”或“改进迁移”，未完成项有明确记录。
- 没有把只有接口的能力标记为可用。

### P2：实时监控与自动化整合

**目标**：让用户能够观察系统实际状态，并根据真实事件自动协调三种方案。

顺序：

1. 完成 CPU/GPU/内存核心实时采样；磁盘和网络指标按可靠采样源逐步增加。
2. 完成必要的监控传输、过期数据处理和 CLI 订阅；不提前建设通用遥测平台。
3. 完成旧版四种触发器迁移及必要的优先级、防抖。
4. 完成场景动作与领域方案的关联，以及 CPU、Power、Scheduling 独立仲裁。
5. 完成内部写入识别、外部修改策略、用户接管和必要的退出恢复。
6. 完成当前支持的进程退出、服务重启和休眠唤醒状态处理；复杂历史与命中分析后续按需求增加。

**退出条件**

- 实时监控显示真实样本和数据年龄。
- 旧版场景触发能力保留。
- 场景不再无条件恢复过期快照。
- 自动化可以只作用于一个领域，并能解释基本执行结果。

### P3：系统生命周期与正式交付

**目标**：在 P0 已恢复最小 CLI/Agent 真机连接的基础上，使安装、运行、升级、恢复和卸载形成完整产品链。

包括服务安装升级、驱动管理、配置迁移、开机启动、托盘、休眠唤醒、崩溃恢复、卸载处理、安装包和便携包。PawnIO 的许可证、版本、签名和再分发决策必须在正式打包分发前关闭。

此阶段不是重新实现核心业务，而是将已完成能力可靠交付。P0 的 B1 修复不替代本阶段完整生命周期工作。

### P4：GUI 与扩展生态

**目标**：恢复完整 WPF 用户界面，并为后续模块和插件生态建立受控入口。

- GUI 消费 Agent Contracts/业务能力，不启动 CLI 子进程，不直接引用 Platform。
- GUI 与 CLI 共用领域模型和操作结果。
- GUI 可以按领域分批启动。某一领域的 CLI/Agent Contracts 和关键操作结果稳定后，即可从固定 commit 开始对应 GUI 页面；不必等待全部 P2 监控、场景历史或未来扩展完成。跨领域共享契约仍由 DS 明确基线并通过 PR 交接。
- 基线冻结不要求所有未来能力全部实现；只冻结 GUI 当前阶段依赖的契约，并通过版本化扩展处理后续变化。
- 通过固定基线 commit 和 PR 交接；DS 负责集成。
- 模块 UI 区块由能力和模块声明贡献，不把模块、页面、Provider 混成一个概念。
- 插件运行时另立技术任务，第三方插件默认独立进程。

### P5：后续产品路线

按用户价值和维护成本逐项立项：GPU 调校、监控历史、场景模板、高级匹配、告警、插件分发、配置备份和跨平台能力。每项必须有独立的用户价值、范围、依赖、验收标准和维护成本，不因为“架构预留了”就自动进入开发。

## 6. 开发组织与任务交付规则

### 6.1 主开发者与并行任务

DS 是当前产品主开发者和集成责任人。并行 Agent 适合承担边界明确的源码研究或独立 Provider 实现，不适合各自重写共享架构。

每个并行任务开始前必须声明：

- 目标能力和旧版行为依据；
- 允许修改的文件；
- 不允许修改的共享文件；
- 依赖的 Contracts/接口；
- 交付的代码、测试和证据；
- 是否需要真实硬件。

共享文件通常包括 Domain 模型、Contracts、PlanCoordinator、AgentSession、CLI 入口、配置迁移和公共状态账本。除非主开发者明确分配，不应由多个 Agent 并行修改。

### 6.2 每个功能任务的标准闭环

1. **定点核对**：阅读旧版对应源码、新版对应代码和必要的一手平台资料。
2. **行为列举**：明确保留哪些用户行为、修正哪些缺陷、新增哪些行为。3. **实现**：直接完成从 CLI/Contracts 到 Agent/Domain/Platform 的完整链路。
4. **验证**：只运行本次功能相关测试和必要构建；硬件相关功能按条件进行真机验证。
5. **交付**：说明改动文件、用户可用能力、CLI 用法、验证结果、未验证条件和已知限制。
6. **提交**：形成独立、可审查的 commit 并推送。
7. **更新迁移表**：只更新本次实际完成的条目。

不要把“研究报告”“设计方案”“接口骨架”当作功能交付。

### 6.3 测试尺度

保留必要验证，但不把测试变成新的长期阶段：

- 核心算法和规则测试。
- 本次修改的应用、回读、恢复和所有权测试。
- fake Provider 的业务闭环测试。
- 真正需要的硬件写入验证。
- 重要里程碑完成时再做完整构建和测试。

不要求每个小任务重复全量发烟测试、安全审计、异常注入或性能基准。测试必须服务于具体风险和功能正确性。

### 6.4 交付报告格式

每次交付只需回答：

1. 这次让用户新增/恢复了什么能力？
2. 对照旧版保留了哪些行为？
3. 修正了哪些旧版缺陷？
4. 哪些未来扩展点受到影响？
5. 改了哪些关键文件？
6. 执行了哪些必要验证，结果是什么？
7. 哪些内容仍未验证或未完成？
8. commit SHA 与分支是什么？

禁止重复整份项目背景和架构介绍。

## 8. 风险、约束和决策纪律

### 8.1 不能用抽象抹平平台差异

CPU/GPU、电压/频率/功耗、CPU Sets/Affinity、Windows 电源设置等概念存在平台差异。统一的是用户工作流和状态语义，不是强行统一底层参数。

### 8.2 复杂度约束：先满足当前真实功能

只实现当前已有明确用户需求、真实功能依赖或已确认技术约束所要求的复杂度。未来扩展优先通过清晰边界和必要的数据兼容性预留，不提前建设通用框架。

新增抽象前先回答：

1. 当前哪个真实功能需要它？
2. 不引入它会造成什么具体问题？
3. 是否能用已有机制更简单地实现？

如果没有明确答案，就先不实现。未来需求出现时再扩展。不要把抽象数量、状态数量、层级数量或配置项数量当作架构质量指标。

### 8.3 软件验证与硬件验证必须分账

无对应 Intel/GPU 设备时，使用 fake Provider 验证调用链、数据结构、结果语义和恢复流程。真实硬件验证单独标记，不得伪造通过，也不得阻塞其他独立领域的软件开发。

但 fake Provider 不能证明硬件行为。CO 掩码、物理核心映射、SMU 命令接受、FMax 实际生效、APOB 与替代拓扑来源的等价性、S3/Modern Standby 唤醒后的硬件状态，都必须由对应硬件、管理员权限和真实生命周期条件下的证据验证。未经验证的项目只能标记为待真机验证，不得标记为行为等价。

### 8.4 不以新架构为理由删减功能

若要删减旧版能力，必须提供：
- 旧版对应实现和使用行为；
- 保留它的成本或风险；
- 不迁移的具体理由；
- 用户可用的替代方式；
- 对配置兼容和既有用户的影响。

没有这份说明，不应默认删除。

### 8.5 决策记录

涉及领域边界、配置格式、平台支持矩阵、插件 API、权限模型和持久化策略的重大决定，记录在 ADR。一般实现细节不需要新建 ADR。每项决策记录目标、约束、证据、代价、否决选项和推翻决策所需的新证据。

## 10. 本计划的维护规则

- 本文是路线基线，不是每次交付都要复制的报告。
- 新证据可以修改具体任务和优先级，但必须说明修改理由。
- 已完成任务以代码、测试、硬件验证和 commit 为依据，不以口头声明或文档勾选为依据。
- 旧版功能盘点负责记录旧版事实；本计划负责定义迁移和演进路线；逐功能迁移表负责跟踪实际状态；ADR 负责记录重大设计决策。四者职责不互相替代。
- 每完成一个领域，更新迁移表和本计划对应状态；不要反复改写总计划。
- 若当前产品实现与本文冲突，先判断是代码未完成、文档过时，还是计划需要修订，不得默认以文档覆盖代码事实。

**最终产品判断标准：新版不只是架构上比旧版更合理，而是至少恢复旧版已经交付的有效能力，并在状态正确性、自动化、平台扩展、监控、诊断和后续插件能力上形成可验证的进步。**
