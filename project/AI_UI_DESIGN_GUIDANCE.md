# AI 界面设计与视觉评审指导

- **状态**：项目级 AI 工作指导
- **适用范围**：Zentwik Flutter 桌面前端的界面设计、实现、调整与评审
- **参考来源**：[edisonmbli/refactoring-ui-skill](https://github.com/edisonmbli/refactoring-ui-skill)
- **性质**：对外部设计方法的轻量转述与项目适配，不是新的产品 UI 规范或视觉设计系统

## 1. 目的

本文件为 AI 提供界面工作的设计判断方法和执行纪律。它不是界面生成器，也不要求 AI 套用某种固定风格。

核心要求：**先判断界面是否清晰、可理解、可操作，再处理装饰；先诊断问题，再修改；完成实现后进行独立视觉检查。**

## 2. 开始前先识别现状

动手前，先从仓库和实际运行界面确认：

1. 当前前端技术栈、Flutter 版本、桌面平台与窗口行为。
2. 已有主题系统、设计 Token、字体、间距、尺寸、图标和组件约定。
3. 深色/浅色主题、信息密度、界面缩放及用户自定义强调色的处理方式。
4. 当前页面的信息层级、主要任务、操作路径、空状态、加载状态和异常状态。
5. 相关页面及共用组件，避免只优化局部却破坏整体一致性。

已有实现和用户明确决定优先。**不得因为参考资料中的示例值、色板或组件形式而覆盖 Zentwik 现有约定；不得擅自锁定用户自定义的强调色。**

Zentwik 当前前端方向为 Flutter，C# Worker 通过既定 IPC 边界提供后台能力。界面指导不授权 AI 改动 Worker、领域模型或 IPC 契约。若现存文档仍描述 WPF 实现，应区分历史实现说明与当前 Flutter 目标，不得把 WPF 控件或布局方案机械移植到 Flutter。

## 3. 设计判断原则

### 3.1 信息层级优先

- 先明确页面的主要任务、核心信息和主要操作。
- 区分主要、次要、辅助信息；避免所有内容都使用相同字号、字重、颜色和视觉权重。
- 一个界面应有清晰的视觉焦点。不要把每个操作都做成同等醒目的主按钮。
- 先通过布局、尺寸、留白和字重建立层级，再谨慎使用颜色、边框、阴影和装饰。

### 3.2 布局与间距

- 相关内容应在空间上形成明确分组，组内间距与组间间距应能体现关系。
- 不要让所有元素机械居中，也不要把同一个间距值应用到整个界面。
- 控制内容宽度、对齐方式和信息密度，使用户能快速扫描并理解内容。
- 不为装饰而增加卡片、边框、分割线或嵌套容器；容器应表达真实的分组、层级或交互边界。
- 尊重桌面端窗口尺寸与可调整布局，不把移动端页面简单放大成桌面页面。

### 3.3 字体与可读性

- 用有限且一致的字号、字重和行高建立层级。
- 次要信息可以降低视觉权重，但不能因此变得难以辨认。
- 数值、单位、状态、标签和说明应有稳定且易扫描的排布。
- 不要为了视觉紧凑牺牲关键数据的辨识度。

### 3.4 色彩与对比度

- 先识别项目已有的语义色和主题 Token，再决定具体颜色。
- 颜色应承担语义或层级职责，不要仅为丰富画面而增加颜色。
- 状态不能只依赖颜色表达，还应结合文字、图标或形态。
- 检查文本与背景、控件边界与背景之间的对比度；重要内容在深色和浅色主题下都应可读。
- 参考资料中的色值、色阶和 Tailwind 示例均不是 Zentwik 的默认值。

### 3.5 组件与交互

- 组件外观应服务于其功能和交互状态，不要把所有内容统一包装成卡片。
- 明确默认、悬停、按下、聚焦、禁用、加载、成功、警告和错误状态中实际需要的状态。
- 操作反馈应及时、明确，但避免无意义的重复提示和说明文字。
- 空状态应说明当前状态及可执行的下一步；没有内容时，不应展示无法生效的筛选或操作。
- 交互设计应考虑键盘、鼠标、焦点顺序、可访问性和合理的点击目标。

## 4. AI 工作流程

### A. 新建页面或组件

1. 先理解功能与用户任务，不要先搭空壳或堆装饰。
2. 列出内容层级、主要操作和必要状态。
3. 沿用项目现有主题、Token 和组件；缺失时先说明缺口，不擅自建立第二套体系。
4. 先完成结构与布局，再处理色彩、层次和细节。
5. 实现后运行并检查实际界面。

### B. 优化现有界面

1. 先检查现状并列出具体问题，不要因“看起来不够现代”就整体重写。
2. 按影响排序：信息或操作不可理解、可读性/对比度问题优先；一致性问题其次；纯装饰问题最后。
3. 优先修复结构性原因。不要用阴影、边框、颜色或动画掩盖信息层级和布局问题。
4. 控制修改范围，只改用户要求的部分；其他发现单独报告。
5. 以可审查的小步修改完成，并重新验证。

### C. 视觉评审

评审与实现分开进行。评审阶段先报告问题，不擅自修改未获授权的范围。

每项发现至少说明：

- **严重度**：P0（妨碍理解、操作或可读性）、P1（明显破坏一致性或层级）、P2（细节和 polish）。
- **位置**：具体页面、组件或状态。
- **现状**：实际观察到的问题。
- **依据**：对应的设计原则或项目约定。
- **建议**：可执行的修改方向。

按以下顺序检查，避免先纠结装饰而忽略根本问题：

1. 信息层级与操作优先级
2. 布局、对齐与间距
3. 字体与可读性
4. 色彩、语义与对比度
5. 边界、层次与深度
6. 图标、图像及其他视觉素材
7. 空状态、反馈、动效等收尾细节

## 5. 必须进行实际视觉验证

只读代码不等于完成视觉评审。具备运行条件时：

- 启动应用，检查真实渲染结果，而不只看 Widget 树或样式定义。
- 至少检查常用桌面窗口尺寸，以及窗口缩放、窄窗口和高 DPI 下的布局行为。
- 检查深色与浅色主题；若某项主题尚未实现，应明确标记。
- 检查悬停、焦点、禁用、展开/折叠、空数据和异常等相关状态。
- 修改布局后确认没有溢出、裁切、滚动冲突、意外重排或文字截断。
- 能截图时以截图为依据。无法运行或无法取得截图时，结论必须标为“仅源码检查”，不得声称视觉验证通过。

## 6. 禁止事项

- 不得把 Refactoring UI 的 Web/Tailwind 实现细节当作 Flutter 技术要求。
- 不得直接复制示例色值、间距、字号或组件外观作为项目标准。
- 不得为了套用规则而制造无实际价值的修改。
- 不得擅自替换现有主题系统、设计 Token、组件库或强调色设置。
- 不得把所有信息塞进卡片，也不得把所有操作做成主按钮。
- 不得只凭源码声称界面“看起来正确”。
- 不得在视觉优化名义下改变功能、交互语义、领域行为或用户已确认的产品决策。
- 发现设计原则与 Zentwik 明确约定冲突时，先报告冲突；项目约定优先，除非用户明确决定修改。

## 7. 使用边界

本文件提供 AI 的设计判断、实现流程和评审方法。具体页面结构、导航、首页组件、时间线、交互语义及视觉选择，以用户最新明确决定和正式项目规范为准。

本文件不复制上游 Skill 的完整规则库、脚本、Tailwind 映射或生成器。需要理解具体设计问题时，可查阅上游项目及其引用资料；不要把本文件扩展成独立技能系统。
