# 已知限制与不做的事

本文件收录"有依据、但当前不做或做不到"的条目。**不要把这些当成待办重新开工**，也不要在交付里写成已解决。
每条都写清楚：为什么不修、什么条件下才修、在修复前如何对外表达。

---

## 1. SMU 响应三态（成功 / 未知命令 / 明确拒绝）无法区分

- **现状**：`PawnIoSession.Execute` 只回传 `NTSTATUS` 或 Win32 错误码，SMU 邮箱里的响应值（`0x01` / `0xFE` / `0xFF` / `0xFD`）在模块层就被丢弃。
- **后果**：`RyzenSMU` 返回 `0xFF` 与"驱动打开失败"在上层都表现为一次失败，无法给出不同结论。
- **为什么不在上层修**：`research/02-hardware-access.md` §2.3 已判定——上层拿到的不是原始响应，任何字符串或错误码映射都是猜测。
- **什么条件下修**：`Zentwik.Platform/Windows/PawnIoModules` 换成能回传 SMU 响应的模块（或自写驱动）。届时同步改 `AmdSmuTuningProvider` 的失败分类与账本 `Failure` 文案。
- **修好前如何表达**：失败原因只写"SMU 调用失败（错误码 X）"，**不得**写成"平台不支持""命令不存在""固件拒绝"。

## 2. CO 写入的效果层不可判定

- **现状**：账本只表达"写入被接受 + 寄存器回读一致"。
- **明确的产品边界（2026-11-26 决定）**：产品**不做**频率/功耗/温度观测来验证降压效果。这是硬件与固件行为（PCU 可能接受请求后被下限钳住），软件既不能判定也不能修复。
- **修好前如何表达**：`plans show`/`ledger` 里不得出现"已生效降压"这类话；只写"已写入并回读一致"。
- **不要再提**：任何要求"另测频率/功耗/温度"作为验收条件的规范条款都已删除或标注为非产品职责。

## 3. CPU Sets 与核心停泊

- **现状**：已实现 `PlanCoordinator.WarnCoreParking`——CPU Sets 写入成功后按**当前供电侧**读一次 `CPMINCORES`（`0cc5b647-c1df-4637-891a-dec35c318583`，子组 `54533251-82be-4824-96c1-47b60b740d00`），低于 100 时按方案记一次 WARN，说明实际运行范围可能超出设定集合。本机实测 AC=100 / DC=10，插电时不会触发。
- **不做**：不自动修改用户的电源方案把停泊关掉。那是用户配置，改了就是越权。
- **依据**：老项目 `ProcessWatcher.ParkingSuffix`（只提示不改）+ `PowerPolicyService` 注释。
- **修好前如何表达**：日志 WARN，不进账本状态（CPU Sets 仍是 Applied，写入本身成功了）。

## 4. Intel 通道无真机验证

- **现状**：`IntelMsrTuningProvider` 按 `intel-oc-mailbox.md` 实现（命令字 `0x80000011`/`0x80000010`、bit63 忙位、`Global\Access_Intel_OC_Mailbox` 互斥、写后经读命令回读），但本机是 AMD，只有位域单测。
- **未验证的具体点**：命令字是否被真实固件接受、忙位轮询窗口（200 ms）是否足够、平面位（`1<<8`/`1<<9`）在不同世代的差异、`0x1AD` 位序。
- **什么条件下修**：拿到 Intel 机器（12/13/14 代优先）。
- **修好前如何表达**：`caps` 里 Intel 能力为 `unavailable`（不是 `failed`）；交接文档不得写"Intel 已支持"。

## 5. 休眠唤醒的真实时序未验证

- **现状**：`Win32SuspendResumeNotifications` 已在 Session 0 注册成功（日志有 `系统挂起/恢复通知已注册。`），`ReconcileAfterResumeAsync` 的四态判定有单测。
- **未验证**：真实合盖唤醒的回调时机、2 秒去抖是否够、睡眠期间的账本与实际值偏差。
- **什么条件下修**：用户合盖唤醒后查日志 `系统恢复核对：确认 N，重写 N，用户接管 N，未知 N`。若发现回调丢失，再考虑 `PowerRegisterForEffectivePowerModeNotifications` 或 `WM_POWERBROADCAST`。

## 6. 重启后保持未验证

- **现状**：CO/FMax 的 `PersistsAcrossReboot` 标记来自能力探测与方案内容，没有经过真实重启。
- **风险**：主板可能在 POST 阶段重置 SMU 参数，标记却是 `true`。
- **什么条件下修**：一次真实重启后跑 `tuning` 对比。在此之前不要在界面上承诺"重启后仍生效"。

## 7. APOB 表读核 0 被拒

- **现状**：本机 `0x00000000`（核 0）物理内存读被拒，其余核可读。回退到 CPUID `0x8000001E` + L3 域映射，结果与 APOB 一致。
- **不做**：不为单个核再引入第二条读取通道。
- **依据**：`knowledge/hardware/cpu/amd-smu.md`、A1 交接记录。

## 8. 多处理器组（>64 逻辑处理器）

- **现状**：亲和性掩码只覆盖单个处理器组；超过 64 个逻辑处理器或目标不在组 0 时明确拒绝并说明。
- **不做**：不实现跨组拆分成多次 `SetThreadGroupAffinity`。本机是单组，无法验证。
- **修好前如何表达**：拒绝时文案写"当前平台有 N 个处理器组，跨组绑定尚未支持"，不得静默截断掩码。

## 9. 调度持续执行的开销上限

- **实测（2026-11-26）**：空载 0.052% 单核 / 42 MB；10 条规则（9 条匹配不到进程的无效规则 + 1 条有效）0.833% 单核。
- **构成**：每 2 秒一次 Toolhelp 全表快照（约 1 ms）+ 已绑定进程的读回比对（漂移检测必需）。
- **不做**：不改成老项目那种"只做差集、不读回"。读回是漂移检测与用户接管判定的前提，砍掉等于放弃不变量 8。
- **若仍嫌高**：把轮询周期从 2 秒改 3 秒（参考项目 `cpu-affinity-tool` 的做法），代价是进程启动到被绑定的延迟 +1 秒。改之前问用户。
