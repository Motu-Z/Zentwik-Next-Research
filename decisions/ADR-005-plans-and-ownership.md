# ADR-005：三种方案与状态所有权

- 状态：Accepted
- 日期：2026-11-25
- 相关：`research/01-legacy-inventory.md` §1/§5

## 背景

旧版把"调校 + 调度 + 电源"塞进一条规则，并且明确"退出场景不恢复"。同时 `PlanService` 先保存 `AppliedAt` 再写硬件，写失败时磁盘显示已应用。这两点共同导致：用户机器上实际生效的配置与产品记录的配置长期不一致。

## 决策

1. **CPU 调校方案、电源方案、调度方案是三个独立领域对象**，各有自己的 ID、版本、应用与回滚路径；不存在"当前方案"这种跨领域概念。
2. **场景是协调机制，不是第四种方案**：只声明触发条件、引用哪些方案的哪一版、优先级与退出策略。
3. **状态账本记录所有权**：每个被写对象记录 `PreviousValue / DesiredValue / ActualValue / Source / Owner / Priority / Restorable / Failure`。
4. **用户手动接管优先于自动恢复**：接管后 `Owner=User` 且 `Restorable=false`，场景退出不得覆盖；只有用户显式释放才恢复。
5. **仲裁确定性**：优先级高者胜；同优先级按进入时间早者胜（避免抖动）；再按 ID 序数保证可复现。
6. **回退失败不得静默**：回退失败时保留 `Applied` + `Restorable=true` 供重试，并记录失败原因；不能标成"已恢复"。
7. **写入失败不得写成已应用**：`ActualValue` 与 `DesiredValue` 不一致即判定未生效。

## 已知缺口（必须在 M3 前补）

- **持久化范围**（M2 已补）：`PlanApplyRecord.PersistsAcrossReboot` 由提供者能力决定，AMD CO 为 `true`，Intel MSR 通道实现时须为 `false`。
- **休眠/唤醒重放**：旧版假定 S3 恢复会把 CO 清回出厂，该假设未验证。重放前必须先读实际值，不能无条件重写。

## 后果

正面：用户可以随时手工改配置而不会被"恢复"打架；冲突结果可预测；失败可见。
负面：账本状态机比"快照回写"复杂；需要持久化账本并在服务重启后对账。

## 验证

已覆盖：账本 9 个用例（前值记录、实际值不符判失败、用户接管拦截、低优先级不可抢占、高优先级接管保留原始前值、回退失败保持所有权、释放接管、注入时钟）。

M2 补充（`tests/Zentwik.Core.Tests`）：方案写入后回读并落账本、提供者不可用时判失败且不写账本、用户接管后不被场景覆盖、场景按优先级切换与回退、漂移检测把所有权交给用户、方案版本变更导致场景跳过。

待验证：服务重启后的账本对账、休眠唤醒后的实际值复核。
