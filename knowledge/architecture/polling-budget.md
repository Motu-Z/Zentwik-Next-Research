# 轮询预算与后台开销

- 规范名称：后台轮询的时间与 CPU 预算
- 所属领域：`architecture`
- 核验状态：Verified（本机实测，2026-11-26）
- 相关文档：[lifecycle.md](lifecycle.md)、[scenes-arbitration.md](../domain/scenes-arbitration.md)、[state-ownership.md](../domain/state-ownership.md)

## 1. 为什么单列一篇

旧版反复栽在同一件事上，`CHANGELOG` 里至少三次：「后台采样线程空转占用 CPU」「后台定时器空转」「采样间隔改为 5 秒」。当时的解法是把间隔从 1 秒拉到 5 秒，而不是想清楚"每轮到底在做什么"。

因此本项目定一条规则：**新增任何周期性任务，先回答三个问题**——多久跑一次、每轮碰多少对象、被碰的对象这段时间内真的会变吗。三个问题里有一个答不上来，就不该进循环。

## 2. 当前轮询拓扑

| 循环 | 间隔 | 每轮动作 | 可降频条件 |
|---|---|---|---|
| 场景评估 + 调度 enforce（`SchedulingWatcher`） | 2 秒；无事可做时 20 秒 | 进程快照、逐规则查进程、逐进程读回亲和性与优先级、账本对账 | 无自动场景且账本无持有项 |
| 漂移核对（`DetectDriftAsync`） | 30 秒（自 2026-11-26） | 有 `cpu.co.*` 账本时逐核读固件；逐项回读电源设置 | 无 |
| 核心停泊读取（`CoreParkingPercent`） | 10 秒缓存 | 读一次电源设置项 | 无 |
| 进程名快照（`AffinityScheduler.Find`） | 1 秒 TTL | Toolhelp 快照，只取 PID 与映像名，不 OpenProcess | 无 |
| 遥测推流（`TelemetryHub`） | 客户端订阅，500–5000 ms | 采样 CPU/内存 + 进程计数 + 逐逻辑处理器占用率；进程计数另有 2 秒 TTL；占用率每拍读 | 无订阅者时完全不跑 |
| 日志落盘 | 每 32 行 info；warn/error 立即 | `StreamWriter.WriteLine` + 条件 Flush | 无 |

配置变更走信号唤醒（`NotifyConfigChanged`），不靠缩短间隔换响应速度。遥测只在客户端订阅期间运行，`zentwik monitor` 或桌面端关闭后归零。

## 3. 三条容易踩的坑

**其一，把"读固件"放进高频循环。** 一笔 `cpu.co.*` 账本会让漂移核对读**全部物理核**，因为核偏移是整表返回的。16 核约 9 ms，2 秒一次就是 0.44% 单核，而 CO 值不会在两秒内自己变化。核对周期与"值可能变化的速率"对齐，30 秒足够。

**其二，把"什么都没发生"也当成需要轮询。** 没有自动场景、账本也没有持有项时，2 秒一轮的评估必然全部落空。降频到 20 秒不影响任何正确性，配置变更照样秒级响应。

**其三，逐行 Flush。** 每行日志一次系统调用，高频日志等于拿磁盘当水管用。info 攒 32 行刷一次，warn/error 立刻刷——出问题时最需要的是那两条，而稳态下产出最多的是 info。

**其四，把"只是数一下"当成便宜操作。** 遥测里的进程数原先用 `Process.GetProcesses().Length` 取，单次微基准仅 0.43 ms，看起来可以忽略。但它在 500 ms 订阅下每拍执行一次，每次把全表 300 余个进程建成 `Process` 对象、分配约 360 KB，120 拍累计 40 MB 以上，把 Gen0 GC 拖成了持续开销。端到端实测比单次微基准重要：这一项占了订阅路径 43% 的成本。

**其五，让客户端决定服务端的采样频率而不设下限。** 订阅间隔下限曾是 200 ms，5 Hz 对界面毫无意义，成本却是 2 Hz 的 2.5 倍。下限收到 500 ms。

## 4. 实测（本机 9955HX / 16 核 32 逻辑处理器，2026-11-26/27）

同一代理可执行文件，采样 60 秒 `TotalProcessorTime` 增量。百分比指占**单个逻辑核**的比例，不是整机。

| 场景 | 优化前 | 优化后 | 变化 |
|---|---|---|---|
| 空转（无场景、无方案、无账本） | 125.0 ms / 0.208% | 31.3 ms / 0.052% | −75% |
| 一个自动场景 + 12 个受管进程 + 4 条 CO 账本 | 609.4 ms / 1.016% | 390.6 ms / 0.651% | −36% |
| 500 ms 持续遥测订阅（120 拍） | 984.4 ms / 1.641% | 562.5 ms / 0.938% | −43% |

说明：受管进程的读回（`OpenProcess` + 读亲和性 + 读优先级）属于 enforce 的必要成本，本次未优化。它按进程数线性增长，规则匹配大量同名进程（如 `svchost`）时是下一个观察点。

## 5. 未做但记在账上的

- 每进程每轮两次 `OpenProcess`（读创建时间一次、读状态一次）可合并为一次，收益约每进程 10–20 μs，低于改动风险，暂不做。
- `AffinityScheduler.TakeSnapshot` 建完字典后又整表复制一次为 `Dictionary<string, ProcessTarget[]>`，276 项约 20 μs、2 秒一次，占比 0.15%，评估后不改。
- `state.json` 全量重写 + `FlushFileBuffers` 只在账本或配置真变化时触发；若将来出现"每轮都有变化"的路径，这是首先怀疑的地方。
- 日志尚无旧版 `LogThrottle` 那类按"消息 + 时间窗"的重复抑制，只在刷盘频率上做了收敛。
- ~~多个客户端同时订阅时各自采样一遍，`TelemetryHub` 没有按时间的采样缓存。~~ 2026-11-27 已按传感器间隔缓存：两次硬件读取之间沿用上一次读数（见 §9）。

## 6. 进程数与僵尸条目

Toolhelp 快照会列出已退出但对象尚未回收的进程（`ThreadCount == 0`），这类条目会让计数虚高，也会让调度对死 PID 反复 `OpenProcess` 失败。`NativeProcessList` 的计数与快照采集都按线程数过滤。

口径变化：同样时刻，`Process.GetProcesses()` 报 276，Toolhelp 过滤后 309，`Get-Process` 306。原实现少报约 33 个（受保护/跨会话进程），新口径更接近任务管理器。

## 7. 曾有的 API 黑名单（2026-11-28 移除）

`tests/Zentwik.Core.Tests/PerformanceGuardTests.cs` 已于 2026-11-28 删除。它曾扫描 `src/` 全部源码（跳过注释与构建输出），命中下列字符串即测试失败：`System.Management` / `ManagementObjectSearcher` / `ManagementObject` / `PerformanceCounter` / `GetProcessesByName` / `Process.GetProcesses` / `ServiceController`。

**移除理由（用户判定）**：字符串黑名单挡住的只是旧版**已经修过**的那几个坑，挡不住设计层面的浪费。同期的三处真实缺陷没有一处落在名单覆盖范围内，反例都是本工程自己造的：

| 缺陷 | 用到什么 | 黑名单管得着吗 |
|---|---|---|
| 逐核频率在每次传感器采样时绑核读 16 个物理核，订阅期上下文切换 23.5k → 71.7k/s | `SetThreadAffinityMask` + MSR 读 | 管不着 |
| `modules disable` 只改状态，不停订阅、不释放 PawnIO/SMN 会话、不回退账本 | 无（逻辑没写） | 管不着 |
| 模块开关除 `power-limits` 外无入口强制，是标签不是开关 | 无（设计缺陷） | 管不着 |

因此它从"性能护栏"降级为一个**回归绊线**（防止把旧版修过的东西手滑写回来），不构成质量保证。把它当成"架构有边界、老版靠人记"的证据是偷换——2026-11-28 用户当场指出。

**来源待考**：该测试此前被本文写成一条设计决定，但仓库与研究记录中均无用户要求的痕迹。用户 2026-11-28 明确表示"强行禁止没有意义"。不要再把它当作共识引用。

**仍然成立的是背后的事实**，它们是选型依据而非禁则：WMI 会拉起 Winmgmt 并让调用方同步等待（旧版曾因调度用 WMI 查进程把系统拖到半崩）；`PerformanceCounter` 首次访问要加载计数器库；`GetProcessesByName` 每次枚举全表。选实现时照此判断，不靠名单兜底。

另有一条不写成测试的约定：**不要调用 `timeBeginPeriod`** 提高定时器精度。它会拉高全系统功耗与唤醒频率，收益仅是让 2 秒轮询更准时。

**替代方向（未实现）**：用端到端开销门槛代替黑名单——订阅 60 秒内自身 CPU 增量、系统上下文切换涨幅超过阈值即失败。这类测试能捕捉"每拍多做了一件事"，字符串匹配永远不能。未实现前不得对外声称开销受测试保护。

## 9. 哪些间隔交给用户，哪些不给（2026-11-27 约定）

判据只有一条：**改动只影响数据新鲜度与自身开销的，开放配置；会改变系统状态、仲裁结果或写入行为的，固定并写明理由。**

### 9.1 开放（用户可改）

| 间隔 | 位置 | 范围 | 默认 | 端点 |
|---|---|---|---|---|
| 监控推送间隔 | `UserSettings.MonitorIntervalMs` | 500–5000 ms | 1000 ms | `zentwik settings --monitor-interval`、`zentwik monitor --interval` |
| CPU 传感器读取间隔（温度 / 封装功耗 / 逐核频率同一拍读） | `UserSettings.SensorIntervalMs` | 500–30000 ms | 1000 ms | `zentwik settings --sensor-interval`、`zentwik monitor --sensor-interval` |

- 两者只决定"看到的刷新快慢"和"读硬件的次数"，不改变任何硬件或进程状态，改错最多是更耗电或数据更旧。
- 命令行参数只覆盖本次订阅，持久值在设置里：`zentwik monitor` 不带参数时按设置采样。
- 服务端把请求值夹到上下限并在 ack 里回实际生效值，客户端按 ack 算超时——不能用请求值，否则被抬到下限时会误报超时。
- 传感器读硬件的成本比读系统计数器高一个量级（SMN 读要拿 `Global\Access_PCI` 互斥，逐核频率要绑核 16 次），所以传感器间隔独立于推送间隔：两次读取之间沿用上一次读数。
- **节奏按拍数算，不按时间戳**：`(tick - 1) % round(sensor/interval) == 0`。用"距上次读取是否已满间隔"判断时，`PeriodicTimer` 抖到 994 ms 的那一拍会被判成未到点，实际变成两拍一读（传感器间隔 1 秒 → 真的 2 秒），2026-11-27 实测踩到。代价是传感器节奏被量化到整拍（1500 ms 传感器 + 1000 ms 推送 = 2 拍）。
- 逐核频率单帧成本：空闲 0.23 ms（16 核 × 2 次 MSR 读 + 16 次绑核）；全核满载时绑核要等时间片，临时把采样线程提到 `Highest` 后从 50–160 ms 降到 0.4–1.2 ms，读完立即还原。

### 9.2 不开放（保持内部固定）

| 间隔 | 现值 | 不开放的理由 |
|---|---|---|
| 场景评估 + 调度纠偏 | 2 秒（无自动场景且账本空时降 20 秒） | 直接决定"进程启动到绑核"的延迟与场景切换的及时性；调坏会让用户以为绑定失败 |
| 漂移核对 | 30 秒 | 改快等于按倍数重复读全部物理核（一笔 `cpu.co.*` 账本 16 核约 9 ms），是纯开销 |
| 电源方案/功耗墙写入后的回读 | 立即 | 回读是写入正确性的一部分，不是可调参数 |
| 进程计数的 2 秒 TTL | 2 秒 | 内部节流，不是采样语义；暴露出去只会让"进程数为什么没变"变成问题 |

- 这些值都在源码常量里，改它们是改行为，须走评估而不是配置。

逐逻辑处理器占用率**每拍随推送读，不单独开放间隔**：它一次 `NtQuerySystemInformation(SystemProcessorPerformanceInformation)` 拿整张表（32 逻辑处理器一条调用），单次成本微秒级、无分配压力，属于"读系统计数器"那一类，与温度/功耗的"读硬件要拿互斥"不同。与其把它做成第三个可配间隔，不如就让它跟着推送走——它本身就是对"这拍的 CPU 总占用摊到了哪些核"的即时解释。真机（9955HX，32 逻辑处理器）实测输出分布正常，能看出忙核集中在少数几个，单帧 `cpu 0.0%` 时逐核也都接近 0。

监控历史（`telemetry.history`）**只在订阅期间积累，不常驻采样、不落盘**：历史是 3600 帧的环形缓冲，采样即写入。做成常驻采样会推翻"无订阅者时遥测完全不跑"这条底线，而落盘等于每秒一次小文件写、还得处理重启后的旧数据口径。取舍是：WPF 打开监控面板（即订阅）后曲线从零长出来，面板关掉历史清空。要跨重启的历史，得先接受"服务常驻低频采样"这个前提，那是一次独立的后台开销决策，不是默认。

### 9.3 落到实现的位置

- 推送与传感器间隔：`TelemetryHub.RunSubscriptionAsync(intervalMs, sensorIntervalMs, …)`，`sensorIntervalMs = 0` 表示不读传感器。
- 温度/功耗/频率通道：`AmdSensorSource`（`ICpuSensorSource`），模块 `AMDFamily17.bin`，能力 `monitor.telemetry.cpu.sensors`；逐核频率在 `SampleClocks` 里绑核采样，与温度、封装功耗同一拍。
- 传感器通道另有 10 秒失败重试节流（会话/模块级失败时），同属内部开销控制，不开放。
