# 研究效率与任务消耗控制

## 目标

以最少的重复劳动获得足以支持产品和架构决策的可靠证据。优化对象是无效调用、重复读取、过度拆分和低价值文档，不是压缩必要的验证。涉及硬件写入、驱动、权限边界、数据安全和不可逆操作时，不得为了节省消耗而跳过验证。

## 1. 任务分级

按问题风险和决策影响选择最低充分深度：

| 等级 | 使用场景 | 最低交付 |
|---|---|---|
| L1 快速调查 | 成熟技术、低风险事实、已有充分资料 | 结论、关键来源、适用条件 |
| L2 比较研究 | 技术选型、领域建模、架构取舍 | 候选比较、证据、成本、风险、推荐 |
| L3 深入验证 | 高风险未知数、关键性能或兼容性问题 | 可复现实验/原型、环境、数据、限制、结论 |

默认从 L1 开始。只有当问题影响关键决策、证据冲突或 L1/L2 无法消除关键未知数时才升级。L3 应有明确的待验证假设和停止条件，不能变成无边界探索。

## 2. 子 Agent 派发规则

- 只有目标相对独立、专业领域不同或确实可以并行时才派发。
- 不以并行数量作为效率指标；可合并的任务应合并。
- 主协调者负责产品整体分析、任务边界、跨领域综合和最终决策，不能把这些工作全部转交出去。
- 子 Agent 默认不再继续派发；确有必要时最多再拆一层，并说明拆分收益。
- 同一代码区域、同一技术问题或同一资料不得由多个 Agent 无目的地重复盘点。
- 每个任务派发时写明：问题、范围、已有资料、需要新增的证据、交付路径、完成标准。
- 子任务应交付可供其他任务直接引用的结论和证据，而不只是聊天摘要。

## 3. 共享资料与避免重复

开始研究前，先检查研究仓库已有报告、原型、ADR 和索引。

- 已有结论仍适用于当前版本时直接复用，并注明引用文件和版本/日期。
- 只研究尚未解决的部分，不重复生成完整背景介绍。
- 旧项目事实以明确的提交或版本为基准；若当前源码变化可能影响结论，再重新核验。
- 对源码盘点优先建立文件/符号索引和领域地图，后续任务按需读取相关范围，不要求所有 Agent 从头扫描整个仓库。
- 对同一事实建立一个主要维护位置，其他文档引用它，避免多份文档复制同一段内容。
- 发现旧结论错误、证据过期或前提变化时，明确指出差异并更新原成果，不要静默覆盖。

建议逐步维护以下共享资料：
- 旧版功能与实现盘点
- 领域/源码导航索引
- 技术预研报告
- 风险与未决问题清单
- 架构决策记录（ADR）

## 4. Skill 使用策略

Skill 是工作方法，不是每个任务都必须完整执行的流水线。根据任务阶段选择相关 Skill，避免多个 Skill 对同一工作重复要求。

| Skill | 适用阶段 | 使用原则 |
|---|---|---|
| Acquire Codebase Knowledge | 初始代码库盘点、重大结构变化 | 建立一次可复用的代码库知识基线；局部任务只补充相关部分 |
| investigate-codebase | 定位具体实现、调用链、数据流 | 针对明确问题使用，不与全仓库盘点重复 |
| Technical Spike | 关键技术未知数验证 | 一次只验证一个核心问题；设时间/范围盒和停止条件 |
| Writing Plans | 研究结论转实施计划 | 仅在准备实施时使用，不为每份研究报告都生成实施计划 |
| Architecture Decision Records | 需要形成正式架构选择时 | 记录真正影响长期结构的决策；一般观察不必建 ADR |
| Subagent-Driven Development | 已有明确实施计划的多步骤开发 | 用于隔离实施、任务级评审和整体验收；不把它用于普通资料收集 |
| Doubt-Driven Development | 非平凡结论、关键推荐和争议点 | 有界反证审查；聚焦可能改变决策的主张，不要求所有细节都重复辩论 |
| Code Review Excellence | 代码变更或原型评审 | 对实际 diff 和行为评审，不对纯研究文字重复做代码评审 |
| Debugging Strategies | 已出现可复现故障或异常行为 | 先建立复现和证据链；不要把常规技术调查包装成调试任务 |

### Skill 组合建议

- 初始盘点：Acquire Codebase Knowledge；必要时用 investigate-codebase 补查具体调用链。
- 技术预研：Technical Spike；关键结论再用 Doubt-Driven Development 反证。
- 架构收敛：Architecture Decision Records。
- 实施准备：Writing Plans。
- 实施阶段：Subagent-Driven Development；完成后用 Code Review Excellence。
- 故障阶段：Debugging Strategies。

不要为了“启用 Skill”而强行调用它。一个任务通常只需要一个主 Skill，最多搭配一个针对性复核 Skill。

## 5. 研究输出控制

报告以决策信息为中心，优先采用以下结构：

1. 结论与推荐
2. 证据及其来源/版本
3. 适用条件和反例
4. 风险、未知数与置信度
5. 对 Zentwik 的具体影响
6. 下一步验证或决策

背景知识只保留理解结论所必需的部分。长篇资料、命令输出和实验细节放入附录或独立文件。不要在多个报告中重复粘贴通用技术介绍。

每份报告明确区分：
- 已验证事实
- 基于事实的推断
- 尚未验证的假设
- 建议或个人判断

## 6. 停止与升级条件

满足以下任一条件时，可以结束当前研究：
- 证据足以支持当前决策，剩余未知数不会改变选择。
- 新一轮研究预计不会显著改变结论。
- 剩余风险更适合通过后续原型、集成测试或真实硬件验证解决。
- 问题已超出本轮范围，且继续研究的收益低于成本。

遇到以下情况应升级研究深度：
- 关键来源互相矛盾。
- 结论依赖尚未验证的硬件/驱动行为。
- 方案可能造成系统不稳定、数据损坏或权限越界。
- 性能结论缺少可重复测量。
- 技术选择会形成高成本、难以逆转的长期约束。

停止研究不等于掩盖不确定性。应保留未决问题、影响范围和后续验证方式。

## 7. 本项目第一轮的建议执行顺序

1. 建立旧项目功能/源码基线，避免所有领域 Agent 重复全仓扫描。
2. 根据功能盘点形成产品能力清单，区分迁移、补全、新增和暂缓。
3. 并行研究真正独立的高影响领域：硬件访问、桌面 UI、服务与 IPC、领域/自动化模型、模块与插件。
4. 将跨领域约束交由主协调者综合，整理候选架构和关键分歧。
5. 只对会改变架构选择的高风险未知数制作原型。
6. 形成 ADR 和下一阶段实施计划。

不要在第一轮研究尚未收敛时生成完整产品实现，也不要为了报告数量而给每个子领域强制安排一份长报告。

## 8. 模型、上下文与对话管理

目标是降低实际输入/输出 token，而不是一味追求最大窗口。

### 推荐默认值

| 设置 | 默认 | 提高条件 |
|---|---|---|
| 思考强度 | 高 | 关键架构决策、高风险分析或复杂矛盾才用极致；常规检索和整理用低 |
| 上下文窗口 | 300K | 跨多个领域综合或大量源码同时分析时用 600K；确有超大输入需求才用 1M |

窗口大小是容量上限，不代表每次都会消耗整个窗口；实际计费和 WorkBuddy 的档位映射以其当前界面/文档为准。不要假定 WorkBuddy 的“低/高/极致”与模型 API 参数完全等价。

### 控制上下文

- 只提供当前任务所需文件；优先索引、搜索和定点读取，不要反复加载整个仓库。
- 先查研究仓库，引用已有结论；不要把完整旧报告复制进提示词。
- 提示词只写目标、约束、输入位置、交付物和验收标准。
- 输出先给结论和证据；长日志、原始数据及完整命令输出写入文件，聊天只报告路径和摘要。
- 不要求 Agent 重述已知背景，也不要让多个 Agent 各自生成相同的总结。
- 不为使用大窗口而扩大任务范围。

### 对话切换与交接

对话是临时工作区，GitHub 研究仓库才是长期事实来源。

- 按研究阶段或独立领域切换对话，不要让一个对话承担整个项目。
- 若平台显示上下文使用率，可在约 60%–70% 时准备交接，接近 80% 前完成切换；这是操作经验值，不是模型硬性阈值。
- 若不显示使用率，在阶段完成、主题明显改变、历史内容开始干扰当前任务或需要反复纠正旧上下文时切换。
- 切换前只生成简短交接：目标、已完成事项及文件路径、已确认结论、未决问题、下一步、禁止重复的工作。
- 新对话先读取交接文件和相关研究成果，再继续；不要复制整段聊天历史。
- 重要结论必须先写入仓库再切换，不能只留在旧对话中。

建议交接文件放在 `research/handoffs/`，按阶段命名。若交接内容很少，可直接写入对应阶段报告，不必为了形式新建文件。
