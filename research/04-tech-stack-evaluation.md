# 04 · 技术栈评估（全栈）

- 状态：已完成（含一组实测数据，其余为文档/源码证据）
- 日期：2026-11-25
- 环境：Windows 11 26300 / Ryzen 9 9955HX（32 线程）/ 31.2 GB / RTX 5070 Ti Laptop + Radeon 610M
- 工具链实测：.NET SDK 10.0.401、10.0.403，运行时 10.0.14；**无 Rust/cargo**；cl.exe 19.51 存在但不在 PATH；无 CMake、无 Qt SDK；Node 22.22
- 基线：旧项目 `Zentwik` @ `bc3c59b`（.NET 10 + WPF + 提权 Worker + 命名管道，协议 v23，46 命令）

## 1. 结论

| 层 | 选择 | 置信度 |
|---|---|---|
| 语言/运行时 | C# / .NET 10 | 高 |
| 桌面 UI | WPF（自绘图表，不用第三方图表库） | 中高 |
| 特权进程 | LocalSystem 服务，NativeAOT | 中 |
| UI ↔ 服务 | 命名管道，长度前缀帧 + 多路复用 + 事件订阅 | 中高 |
| 硬件访问 | 分层：用户态只读 / 特权写 / PawnIO 单进程独占 | 高（沿用已验证链路） |
| 模块与插件 | 进程内模块 + 进程外插件宿主（后置） | 中 |
| 数据存储 | JSON 文档 + 原子替换，方案/设置/账本分文件 | 高 |
| 安装/更新 | MSI（WiX）或 Inno，服务注册 + 事务回滚 | 中（未验证） |

一句话：**保留 .NET，但这次不是因为旧项目是 .NET**——硬件访问全部经 PawnIO 驱动 IOCTL 与 Win32 API，语言能力没有差异；C++ 的唯一优势（可直接写内核驱动）在本项目不存在，因为签名版 PawnIO 只加载维护者签名的模块，自造驱动不可分发。Rust 的优势（内存安全、小体积）落在一条很窄的 IOCTL 封送层上，代价是一整套新工具链和双语言边界。

## 2. 评估权重

按项目真实风险排序，而不是按语言流行度：

1. 硬件写入安全与状态正确性（错一次可能让机器不稳定）
2. 长期维护成本（单人 + 时间有限）
3. 权限边界与进程生命周期
4. 高密度数据展示与可访问性
5. 扩展能力（模块/插件）
6. 体积、启动、内存
7. 跨平台（**明确非 v1 目标**）

第 1、2 项权重最高，且都与语言无关，主要取决于领域建模、测试和隔离设计。这一点决定了整份评估的重心：不应该用"哪个语言更快"来选。

## 3. 语言与运行时

| 维度 | C# / .NET 10 | Rust | C++ |
|---|---|---|---|
| Win32 / COM 互操作 | 源生成 `LibraryImport`，P/Invoke 与结构体封送成熟；MS Learn 与生态样例最全 | `windows` crate 质量高，但每个 API 都要手写安全包装，样板多 | 最直接，但生命周期与错误处理全靠人工 |
| 驱动访问 | PawnIO IOCTL 与语言无关 | 同 | 同 |
| 可否自写驱动 | 不可分发（签名） | 不可分发 | 不可分发 |
| AOT / 体积 | 服务可 NativeAOT（约 10–20 MB），UI 不可 AOT | 全原生，约 5 MB | 全原生 |
| 内存安全 | 有 GC，`unsafe` 面可控 | 编译期保证 | 无 |
| 迭代速度 | 快（热重载、调试器、异常栈完整） | 慢（借用检查 + 长编译） | 慢 + 缺陷成本最高 |
| 生态（本项目相关） | LibreHardwareMonitor、SMUDebugTool 参考实现、WMI/注册表/服务模板齐全 | 相对薄，需自建 | 中等但需自建构建系统 |
| 本机可构建 | **已验证**（39 个测试通过） | 未安装 | 可编译但无 CMake/Qt |
| 单人长期维护 | 最优 | 中 | 最差 |

结论：C#。淘汰 C++ 的理由不是"难"，而是它的核心优势在本项目被签名策略直接抹掉，剩下的只有更高的缺陷成本。淘汰 Rust 的理由是成本与收益不匹配，而不是能力不足——**如果将来把特权核心单独做安全评审，Rust 重写 `Zentwik.Platform.Windows` 这一层是可行且有价值的**，接口已经按此预留。

## 4. UI 框架

### 4.1 实测（8 序列 × 600 点，整块重绘，10 秒）

同一台机器、同一份测量代码，Release、JIT（未开 AOT）、默认主题：

| 场景 | 渲染 p50 | p95 | max | 实际帧率 | 帧间隔 p50 | 进程 CPU（%单核） | RSS |
|---|---|---|---|---|---|---|---|
| WPF 10 Hz | 0.254 ms | 0.798 ms | 18.2 ms | 9.1 Hz | 108.9 ms | 16.6% | 120 MB |
| Avalonia 10 Hz | 0.303 ms | 0.687 ms | 11.7 ms | 9.1 Hz | 109.1 ms | 29.4% | 237 MB |
| WPF 60 Hz | 0.195 ms | 0.446 ms | 12.2 ms | 39.8 Hz | 30.5 ms | 44.1% | 172 MB |
| Avalonia 60 Hz | 0.235 ms | 0.582 ms | 9.6 ms | 44.1 Hz | 18.1 ms | 82.7% | 287 MB |

读法：
- 两种框架的**单帧绘制成本都在 0.2–0.3 ms**，对 10 Hz 数据面（100 ms 预算）完全不是瓶颈。图表性能不构成选型依据。
- Avalonia 在本机内存高约 2 倍、CPU 高约 1.8 倍。这与"Skia 更轻"的直觉相反，原因未查清（可能含默认主题、合成器路径、JIT、双 GPU 切换）。**这是一个反例，不是定论**：没有开 AOT、没有调渲染选项，不能据此断言 Avalonia 更差。
- 60 Hz 两种框架都达不到：`DispatcherTimer` 受系统定时器粒度限制（WPF 实际 39.8 Hz）。要真 60 Hz 必须用 vsync 回调（`CompositionTarget.Rendering` / `RequestAnimationFrame`）。**产品只需要 4–10 Hz 数据面**，不要为此引入复杂度。

原型代码：`prototypes/ui-spike/{WpfSpike,AvaloniaSpike}`，结果文件在各自 `bin/Release/.../result-*.txt`。

### 4.3 为什么最终是 WPF

不是因为旧项目用它，而是三条证据：

1. **产品域是 Windows 专属**。电源方案、CPU Sets、PawnIO、MSR 全部只有 Windows 实现。跨平台 UI 在没有跨平台域的情况下只是打包姿态，Avalonia 的主要优势因此被中和。
2. **可访问性是一等需求，WPF 是唯一经过长期验证的 .NET 桌面方案**。Avalonia 12 有 peer 与 `AutomationProperties`，但没有实测，不能把"文档里有"当成"能用"。
3. **实测中性**：图表成本两者相同，Avalonia 在本机反而更重。

淘汰理由：
- **WinUI 3**：引入 Windows App SDK 运行时依赖与 MSIX/自包含打包复杂度；无内置托盘（本产品需要）；数据密集表格表现口碑差；未在本机验证构建。作为"未来若必须用 Fluent 原生控件"的备选保留。
- **Avalonia 12**：保留为**跨平台成为真实需求时的第一替代**。切换成本被刻意压低（见 §10）。
  - **漏洞归因更正（2026-11-26，一手核实；详见 ADR-002 否决项勘误）**：`Tmds.DBus.Protocol 0.21.2` 属 **Avalonia 11.3.x**（`Avalonia.FreeDesktop 11.3.0` 传递依赖），不是 Avalonia 12。Avalonia 12.0.0 搭载 **0.90.3**（同样落在 GHSA-xrw6-gwf8-vvr9 / CVE-2026-39959 受影响范围 `>=0.22.0,<0.92.0`，High/CVSS 7.1），12.0.1 升级到 **0.92.0** 才修复。"Windows 运行时不走 D-Bus 路径"只说明运行时不加载 Linux 后端，但 NuGet 审计按 TFM 依赖图判断：默认 `direct` 模式不审传递依赖故通常无 NU1903，改 `all` 模式会报。回滚时应选 12.0.1+ 并把审计模式纳入评估。
- **Tauri 2**：需 Rust + WebView2，双语言边界正好落在最危险的硬件封送层；托盘、服务、驱动安装仍要 Win32。收益（体积）与本项目无关。
- **Qt 6**：无 SDK、LGPL 动态链接约束、C++ 维护成本；优势（图表、原生性能）在 10 Hz 场景用不上。

## 5. 进程与服务架构

| 形态 | UAC 次数 | 会话隔离 | 崩溃独立性 | 升级替换 | 结论 |
|---|---|---|---|---|---|
| 每用户提权 Worker（旧版） | 每次登录/启动 | 跨会话不可见 | 好 | 需停进程 | 淘汰：提权边界随用户态漂移 |
| LocalSystem 服务 + 中完整性 UI | 仅安装时 | 服务在 Session 0 | 最好 | 服务控制管理器可停启 | **采用** |
| 计划任务提权 | 首次 | 差 | 中 | 差 | 淘汰 |

服务承担：PawnIO 句柄独占、SMU/MSR 写入、电源与调度写入、场景引擎、遥测采样。UI 只发命令与订阅事件。**设备句柄不得通过 IPC 传递或复制**——旧版两个进程可同时持有 `\Device\PawnIO` 且无跨进程仲裁。

## 6. IPC

采用：命名管道 + 4 字节长度前缀 + JSON 正文（M1 现状），演进方向：

- 单连接多路复用（`Id` 关联请求响应），事件帧 `Id=0`。
- 背压分类：遥测丢最新并计数、响应永不丢、状态事件 latest-wins。
- 版本协商：主版本 + 能力位，替代旧版单一 `ProtocolVersion=23` 的"任何变更都拒绝"。
- 授权：显式 DACL + `PIPE_REJECT_REMOTE_CLIENTS` + 服务端校验调用方 SID/完整性级别/会话，**不能只按用户 SID 放行**（旧版缺口：同用户任意中完整性进程可下发 SMU 写入）。
- 遥测改二进制列式编码的前提是实测证明 JSON 有成本；当前 4–10 Hz、单帧 < 1 KB，暂无证据支持提前优化。

## 7. 硬件访问分层

- L0 用户态只读：`GetSystemTimes`、`GlobalMemoryStatusEx`、`PowerGetActiveScheme`、注册表 CPU 标识——无需提权，监控在未提权时仍可用。
- L1 特权写：电源方案、CPU Sets/亲和性、进程优先级——服务内执行，写后回读校验。
- L2 内核代理：PawnIO 已签名模块，服务独占句柄；驱动不随包安装，检测→引导官方安装器。
- 能力状态必须是三态以上的枚举（NotSupported / DriverUnavailable / ProbeFailed），不能压成 bool；单项不可用不得让产品整体失效。

## 8. 模块与插件

- 模块 = 声明 ID/版本/能力/依赖/平台要求 + 生命周期（Installed/Enabled/Loaded/Running/Degraded/Failed）。
- 内置模块在进程内；官方扩展同签名同进程；第三方插件独立进程 + 受控 IPC，权限按方法声明。
- 内部模块 API 不自动成为稳定插件 API：插件契约单独版本化，避免内部重构被外部锁死。

## 9. 数据存储

JSON 文档 + 临时文件替换（已验证：写入中断不留半截文件）。分文件存放设置、方案、场景、账本，避免一个巨型文件把无关写入串行化。方案持久化必须带 `planType` 判别字段；状态必须区分期望值/实际值/来源（旧版教训：先落盘打 `AppliedAt` 再写硬件，失败后磁盘与硬件不一致）。

## 10. 对当前骨架的判定

**保留，不重建。** 理由：`Zentwik.Contracts / Domain / Platform / Agent / Cli` 与 UI 框架无关，39 个测试覆盖了账本所有权、场景仲裁、帧编解码、真实管道往返、设置落盘。WPF 壳经实测支持，且是本次评估的胜出项。

需要调整的部分（不扩大范围，逐条落地）：
1. 图表现用 `Polyline` 每次替换点集。10 Hz、120 点足够，但多序列场景应换成自绘 `StreamGeometry`（实测路径）。**暂不动**，列入 M2。
2. ViewModel 已无 WPF 类型依赖，保持；为可访问性补 `AutomationProperties`（M2）。
3. 服务形态未落地：当前 Agent 是控制台进程，需改 Windows 服务 + 会话内 UI 连接（M2）。
4. 管道授权只有 `PipeOptions.CurrentUserOnly`，服务化后必须换成显式 DACL + 调用方校验（M2，安全项）。
