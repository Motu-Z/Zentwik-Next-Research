### B1 服务与 Session 0 通信（本轮修复一半）

## 6. 本轮修复（真机验证过程中暴露）

1. **账本前值陈旧**（`6510d3c`）：所有权已释放（Reverted/Failed）时再次应用，原实现沿用旧 `PreviousValue`，`revert` 会把目标写回陈旧快照，覆盖用户此后的手动修改。现按"仍持有则保留基线，已释放则以当前实际值为新基线"处理，`currentValue` 读不到时保守保留旧值。

4. **PID 复用**（`7dff0be`）：`LedgerEntry` 新增 `ProcessStartTicks`，`Acquire` 写入、清理与回退按创建时间比对。同 PID 的新进程：直接应用路径先丢弃旧条目，持续执行路径判为"已退出"，回退时跳过。旧账本条目该字段为 0，按"进程存活即视为同一目标"保守处理。
5. **状态文件健壮性**（`6838064`）：写入改为 `Flush(flushToDisk: true)` 后再替换；读取失败时先备份 `state.json.corrupt` 再按空状态继续，避免下次保存直接覆盖唯一副本。

## 10. 勘误：CPU Sets 与核心停泊

第四轮写的"旧版与新项目均未做停泊检查"**是错的**，原因是没查旧项目源码。

- 旧版 `ProcessWatcher.ParkingSuffix()` 读取 `CPMINCORES`（AC/DC 取当前供电侧，缓存 10 秒），CPU Sets 绑定成功后若 < 100，在日志里追加"核心停泊 N%，实际范围可能更大"。
- 旧版 `PowerPolicyService` 完整读写 `SettingCoreParkingMin = 0cc5b647-c1df-4637-891a-dec35c318583`（子组 `54533251-82be-4824-96c1-47b60b740d00`），并注释说明"CPU Set 是软约束，停泊的核不算可用"。
- 新版完全没有这段。已补：`PlanCoordinator.WarnCoreParking`，CPU Sets 写入成功后读一次 AC/DC 停泊值（取较小值，10 秒缓存），< 100 时按方案记一次 WARN。**不自动关闭停泊**（那是用户电源配置）。

|---|---|---|---|
| 1 | CPU Sets 直接应用路径写入后 `TryReadCpuSets` 结果被丢弃，直接 `Commit`；系统静默拒绝仍记 Applied | 与 `ApplyTarget` 路径不一致；老项目 `ErrorReadbackMismatch=-2` | 回读后按 `CpuSetSpec.TryNormalize` 比对：一致 Commit、不一致 Fail、读不到 MarkUnknown |
| 2 | `PrepareEnforceField` 不传进程创建时间，持续执行写出的账本条目 `ProcessStartTicks=0`，PID 复用后回退会写新进程 | 第四轮 PID 复用修复只覆盖 `ApplyTarget` | 方法增加 `processStartTicks` 参数，三处调用传 `startTicks` |
| 3 | 直接应用路径缺 `DropStaleSchedulingEntries`，PID 复用的旧条目不清 | 与持续执行路径不一致 | 循环开头补 `StartTicksOf` + `DropStaleSchedulingEntries` |
| 4 | `RevertPlanAsync` 判断"是否还有剩余持有"时只数 `Owner == Scene`，直接应用的条目 `Owner == Plan` 被漏，回退失败时 `LastApply` 被误标 `NotApplied` | `OwnerFor("plan:x") = Plan` | 改用 `StateLedger.IsHeld` |

测试增至 162 例（Core 52），新增：CPU Sets 静默拒绝不得记 Applied、停泊 50% 时 CPU Sets 仍为 Applied。

## 12. IPC / 服务审计结论（无需改动）

逐项核对，未发现 P0：

- 接受循环：`IOException` → `continue`（正确），取消 → `break` 并释放实例。
- 拒绝路径：先读请求拿 Id/Op，回 `Unauthorized` 帧再 `DisposeAsync`，客户端能区分"权限拒绝"与"代理崩溃"。
- 帧编解码：4 字节长度前缀 + `ReadAtLeastAsync` 处理半包；长度 ≤ 0 或 > `MaxFrameBytes` 直接拒绝；`ArrayPool` 租借有归还。
- 调用方校验：SID（配置所有者）、完整性级别（默认 Medium）、Session（可选拒绝 Session 0）三项齐全。
- 场景删除：活动场景先 `DeactivateAsync` 回退，再删配置，账本条目不会变孤儿。
- 方案删除：拒绝被场景引用，且拒绝仍持有账本写入的方案。
- 已知可接受项：`RejectAsync` 在客户端不发帧时最多阻塞 2 秒（本地管道 + ACL 限制，风险低）；`AgentSession` 的 `ContinueWith` 不观察异常（`RunAsync` 内部已有顶层 catch 并记日志）。
