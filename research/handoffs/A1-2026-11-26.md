编码口径（与 `knowledge/hardware/cpu/amd-smu.md` §3.1 一致，不在本文件重定义）：
`(ccd<<28)|((core&7)<<20)`（family > 17h）；`(ccd<<28)|((ccx&1)<<24)|((core&3)<<20)`（17h）。

逻辑核索引（0..N-1，操作系统枚举序）仍是方案与账本的核标识，SMU 只收到物理掩码。

## 2. 映射来源与降级策略

1. **APOB 固件映射**：`ZENTWIK_APOB_TABLE` 指向原始表时优先；解析失败直接报 `rejected` 并给原因，不静默换来源。
2. **Windows 拓扑**：CPUID `0x8000001E` 取硬件核号，`GetLogicalProcessorInformationEx(RelationCache)` 的 L3 域切分 CCD，再按 8（17h 为 4）取模得核内序号。校验项：每核线程数一致且 ∈{1,2}、唯一核数 = `PhysicalCoreCount`、每域核数 ≤ 8 且各域核数一致（异构 CCX 不支持）、域内核内序号不撞号、域覆盖全部逻辑处理器、单处理器组。任一不过 → 不可用。
3. **不可用**：`Query()` 返回 `rejected`，`TryReadOffsets`/`TryWriteOffset` 都拒绝执行。**没有** `序号/8` 兜底。

## 3. 证据（本机只读，Ryzen 9 9955HX / Family 1Ah Model 44 / 32 线程）

| 观测 | 结果 |
|---|---|
| `CPUID 0x8000001E` | 核号 0–15，NodeId 恒 0，同核两线程核号相同 |
| `CPUID 0x8000001D`（L3） | level 3，每域 16 个逻辑处理器，32 MB |
| `GetLogicalProcessorInformationEx(RelationCache)` | 两个 L3 域：`0x0000FFFF` 与 `0xFFFF0000` |
| `CPUID 0x80000026` | SMT 1 位 / Core 4 位 / Complex（16 线程）/ Die（32 线程）；`EDX` 是当前 x86APIC ID，取不到 CCD 号 |
| 新解析器输出 | 16 核，logical 0 → CCD0 核0；logical 15 → CCD1 核7；2 CCD × 8 核 × 2 线程 |

结论：本机 CPUID 核号是 **die 内连续编号**，不是复合体内编号，CCD 必须由 L3 域切分——这正是"只用 `core/8`、`core%8`"会错、而必须走映射的原因。

**对历史观测的重新解释**：旧记录里"核 3、核 11 被拒"的两个掩码 `0x00800000`、`0x10800000`，按数值编码分别是 CCD0 核 8 与 CCD1 核 8——两个越界核号。这与"`[23:20]` 是数值字段、SMU 拒绝 ≥8 的核内序号"一致，是**支持**数值编码的旁证，不是平台限制。唯一不合此解释的是掩码 `0x00000000`（核 0）曾被拒，列入遗留项。

## 5. 未验证 / 遗留

1. **CO 读写未在真机验证**：当前会话非管理员，PawnIO 拒绝访问，通道停在 `privilegeMissing`。
2. **掩码 0 的行为**：本机历史记录中核 0（mask `0x00000000`）读命令被拒。可能是固件把 0 视为空核集，也可能是历史参数问题。已把启动探测改为"逐核读、任一成功即可用"，单核异常不会锁死整条通道；仍需管理员会话确认。
3. **拓扑映射与 APOB 物理核号是否等价**：本机无 APOB dump，无法交叉对比。映射来源会写进 `tuning` 的 detail，便于日后对照。
4. **APOB 路径未上机**：PawnIO 无物理内存模块，需要 inpoutx64/WinRing0，或由外部工具 dump 后经 `ZENTWIK_APOB_TABLE` 喂入。
