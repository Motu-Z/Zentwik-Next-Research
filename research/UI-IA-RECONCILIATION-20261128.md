# Zentwik UI 信息架构审计与需求对齐

- 状态：工作审计稿，非正式 ADR；待用户确认后再同步为产品规范
- 日期：2026-11-28
- 范围：研究仓库产品定义、UI/UX 规范、领域规范与 ADR
- 不涉及：产品源码修改、视觉稿、技术栈变更

## 1. 目的

以研究仓库现有定义为基线，对照用户 2026-11-28 明确提出的首页、专项页面、方案、场景和触发器要求，识别已确认内容、文档冲突与未决问题。不得从零发明产品架构，也不得把未确认的推断写成正式规则。

## 2. 用户已明确的要求

1. 首页由主工作区和时间线构成。时间线是首页固定组成部分，默认位于右侧；主工作区由用户按需组织。
2. 监控是可选功能，不应假设所有用户都启用，也不应把监控指标预设为首页普遍的核心内容。
3. CPU、GPU、进程调度、电源策略等属于同层级的专项功能页面。进程调度、电源策略不是场景的下级功能。
4. 场景是更高层级的全局自动化管理，可以调用其他专项页面的方案。
5. 专项功能支持多个方案。参数修改本身不等于应用；用户可以选择保存到方案、应用、保存并应用等操作。
6. 触发器统一属于场景页面，不属于各专项功能页面。
7. 场景调用专项功能的完整方案，不在场景内复制专项参数。
8. 场景始终引用方案最新内容，不做版本钉定或版本区别。
9. 被场景引用的方案删除后，场景中对应功能变为“不修改”，其他功能调用保留。
10. 多场景冲突通过优先级处理。
11. 手动修改不自动等同于应用。用户可以选择让手动修改覆盖原本已应用的相应参数，也允许后续应用操作覆盖相应手动修改。更细的状态与仲裁暂不扩展。

## 4. 主要冲突与修订方向

### 4.1 首页结构

现有 UI_UX_DESIGN_SPEC 将运行记录作为 Bento 组件，未定义固定右侧时间线。用户已明确时间线是首页固定区域，默认在右侧。因此首页应改为两个独立布局区域：

- 主工作区：用户配置的功能组件，独立管理排列、尺寸和内容。
- 时间线：固定属于首页，默认右侧，按时间组织全局事件。

时间线不应参与主工作区的网格/瀑布流计算；主工作区卡片高度变化不应撑开时间线，时间线内容增加也不应改变主工作区布局。

时间线是否可折叠、能否调整宽度、是否允许临时隐藏，用户尚未明确，不能擅自决定。

### 4.2 监控可选

现有 UI 规范将硬件遥测放在顶部脉搏带，并默认挂载系统脉搏。此设计把监控放在了默认首页结构中，与监控可选的要求不一致。

修订方向：
- 不把监控指标设为所有用户必看的全局信息。
- 用户未启用监控时，不因首页默认组件启动持续监控采集。
- 用户启用后，可以将监控组件加入主工作区或进入监控专页。
- 一次性硬件读取、其他功能必要的数据采集、用户主动启用的持续监控、历史数据持久化必须区分；“监控可选”不等于其他功能不能读取必要状态。

### 4.3 专项页面与场景

专项页面是同层级的专业功能域。场景负责跨域协调，不拥有专项参数本体。

当前领域模型明确三种方案：CPU 调校、电源、进程调度。用户本轮提到 CPU、GPU、进程调度、电源策略属于同层级页面，并概括每个功能支持多种方案。这里需要区分：
- “每个功能页面有自己的多方案管理”是用户已表达的产品方向；
- GPU/内存是否成为新的独立 Plan 类型，仍须结合领域研究和产品决策；
- 监控、设置等页面不应被机械套入 Plan 模型。

触发器统一放在场景页。专项页面管理本领域参数、方案及应用状态，不重复建设触发器入口。

### 4.4 方案引用与删除

用户明确场景始终引用最新方案内容，不做版本区分。仓库 AI_WORK_RULES 已记录 PlanRevision 被用户否决并删除，但领域文档和 ADR 仍残留“引用哪一版”等旧表述。应统一修订这些文档。

删除方案后，场景对应配置恢复为“不修改”。但仓库另有安全约束：方案仍被状态账本持有写入时禁止删除。两者需要协调：场景引用可以解除并变为“不修改”，但不能因此跳过账本回退/所有权安全检查，也不能留下孤儿写入。

### 4.5 手动修改与所有权

必须区分至少三个概念：
- 编辑草稿：仅修改 UI 中的待提交参数，不写入实际状态；
- 应用操作：用户明确要求把编辑结果写入实际环境；
- 用户接管：状态账本把对象所有权转交用户，并影响自动恢复资格。

不能把“用户打开页面改了参数”直接等同于 Owner=User。用户本轮还明确允许后续应用覆盖相应手动修改，因此现有“用户接管后自动恢复不得覆盖”的规则需要更精确地区分：普通手动应用是否构成接管、用户是否有显式接管/释放动作、场景后续应用能否覆盖。用户已表示暂不深入这部分，本报告不替用户作出新规则。

## 5. 工作版信息架构

以下是概念分类，不是最终导航顺序：

    Zentwik
    ├── 首页
    │   ├── 主工作区（用户配置）
    │   └── 全局时间线（固定区域，默认右侧）
    ├── 专项功能页面
    │   ├── CPU 调校
    │   ├── GPU 调校（页面规划与技术能力状态分开）
    │   ├── 内存调校（是否纳入及具体能力待研究）
    │   ├── 进程调度
    │   └── 电源策略
    ├── 场景自动化
    │   ├── 场景定义
    │   ├── 触发器
    │   ├── 跨专项功能完整方案调用
    │   ├── 优先级与冲突仲裁
    │   └── 退出行为
    ├── 方案库（聚合入口，不是统一方案对象）
    ├── 监控（可选功能）
    ├── 运行记录与诊断
    └── 系统设置

补充：
- 专项功能是领域分类，不要求 UI 必须使用同名导航分组。
- 场景概念上是全局编排层；它在导航中是否与专项页面并列展示，是导航设计问题。
- 方案库聚合多个独立领域方案，不创建跨领域“当前方案”。
- 时间线是首页展示区；完整运行记录、状态账本和 Agent/Worker 诊断日志不是同一个概念，需明确各自职责与入口。

## 6. 已确认 / 待确认

### 已确认
- 首页主工作区 + 固定右侧时间线。
- 监控可选。
- CPU、GPU、进程调度、电源策略属于同层级专项页面。
- 场景是全局自动化编排；触发器只在场景页。
- 场景调用专项功能完整方案。
- 方案始终使用最新内容；删除后场景对应项变为“不修改”。
- 多场景冲突按优先级。
- 参数编辑、保存、应用是不同动作。

### 待确认
1. “每个功能支持多方案”的适用范围是否只指可配置的专项功能；GPU/内存是否将来成为独立方案类型。
2. 时间线是否可折叠、调宽或临时隐藏。
3. 时间线事件范围、筛选方式、密度和自动滚动行为。
4. 主工作区是否继续采用现有 12 列瀑布流，还是只保留组件自定义而重新评估布局算法。
5. 多场景是否继续按域独立仲裁；同优先级规则是否沿用进入时间与 ID 兜底。
6. 删除方案时若仍有账本持有写入，具体先解除场景引用还是先恢复/释放账本，需遵守现有安全不变量。
7. 手动应用与用户接管的边界；用户本轮明确暂不深入。
8. 场景是否保留独立动作能力（PROJECT_BRIEF 已写明），还是当前 UI 只展示完整方案调用。
9. 监控关闭时其他功能所需的按需采样如何表达。
10. 时间线、运行记录、状态账本和诊断日志的数据关系与入口。

## 7. 影响文件与建议修订顺序

本报告不直接改写以下规范，待用户确认后再同步：
1. project/UI_UX_DESIGN_SPEC.md：优先修订首页结构、监控默认呈现、时间线职责。
2. knowledge/domain/three-plans.md、scenes-arbitration.md、decisions/ADR-005：清除方案版本钉定的过时表述，统一最新方案引用语义及删除行为。
3. knowledge/domain/state-ownership.md 与 ADR-005：后续单独厘清编辑、应用、用户接管，避免误把所有手动修改视为不可覆盖的接管。
4. project/PROJECT_BRIEF.md：只有在确认 GPU/内存等页面的方案模型后，才更新方案领域定义。
